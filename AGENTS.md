# oxide

An optimized AI coding agent CLI written in Rust.

## Layout

The repository is a Cargo workspace. Shared agent code lives in
`crates/core/`; the terminal binary in `crates/cli/` (`main.rs`, `tui/`,
`theme.rs`, `uninstall.rs`); the Tauri desktop app in `crates/desktop/`
(`manager.rs`/`turn.rs`, the window's own command layer, and a single
`oxide_invoke` command the page reaches through the Tauri globals). The Cargo
package names are `oxide-core`, `oxide` (the CLI), and `oxide-desktop`. The VS
Code extension in `editors/vscode/` is a separate pnpm/TypeScript package, not a
Cargo workspace member: it drives the installed `oxide` binary as
`oxide --mode rpc`, with the prompt and any tool approval travelling on the
child's stdin, so it shares the same on-disk configuration and session
tree without linking `oxide-core`. The CLI and desktop link `oxide_core`
directly (`config`, `session`, `runner` for starting a turn, `updates` for the
release a front-end installs, and `theme_view` for themes as CSS-ready colors).
The desktop resolves project trust from the same `trust.json` the CLI uses and
asks **Trust this project?** before loading a project's `.oxide` agents,
commands, skills and plugins, so its harness matches the CLI instead of being
silently dropped. It accepts image/PDF attachments the way the CLI does — paste
from the clipboard or pick files — by passing them to `runner` as inline content
parts (the webview has no on-disk path for a pasted image), and previews each one
as a clickable thumbnail; the webview refuses a file over the core's 20 MB
attachment limit or of a type no provider takes before it is read into a data
URL, and `commands::attachment_parts` reports a refusal from the core instead of
dropping the attachment from the message silently; it also resolves the message's
own `@path` image/PDF references through `oxide_core::media::referenced_attachments`,
so a reference typed in the composer attaches the same files the terminal's does.
The composer completes an `@path` reference the way the terminal's does, because
both ask the same rules: a keystroke that leaves an `@` under the caret asks the
host (`commands::at_suggestions`), `crates/desktop/src/at.rs` turns the webview's
UTF-16 caret into bytes and answers from `oxide_core::at` over a walk of the
project it keeps until the project changes, and the rows are drawn in the command
palette's own box above the composer (`#at-list` in `ui/index.html`) — `↑`/`↓`
walk them, `Enter`/`Tab` takes one, `Escape` closes the list, a folder keeps the
reference open and a file closes it with a space, and an answer for a value the
reader has typed past is dropped rather than painted under a caret it no longer
belongs to; `ui/check-app.mjs` drives every one of those through a stubbed
bridge, and, over the same stub, that the `/` palette lists a skill under its own
name — the row carrying the name, its arguments and the `skill` badge, taking it
completing the composer rather than running it, and the line it completes to
reaching the agent as the prompt the CLI expands, which is what loads the skill. What a finished turn changed is a card of its own: the run's shadow snapshot is diffed against the state it started from, so a file a formatter, a shell command or an MCP server wrote is listed beside the ones a tool call named, and it holds its own height (`flex: none`) so a transcript too tall for the room scrolls the card into view rather than squeezing it to nothing — the transcript is a flex column, and a shrinking card that hides its own overflow clips its rows away. It wears the report's file tile, offers `Undo` before `Review`, and folds what it does not show behind `Show N more file(s)`. The card's `Review` opens the turn over the window: its files on one side, and on the other the selected file's two sides — the state the run found, read out of the shadow snapshot at the card's own baseline by `change_sides`, against what is on disk now, as the aligned lines `oxide_core::diff::lines` hands over, each carrying the number it holds on the side it sits on, with a long stretch neither side changed folded behind its count until it is clicked — a side of it that is not text makes the whole file binary, the same reading the card's own row takes (NUL bytes included, since bytes valid UTF-8 holding one are still a file git calls binary and the review must not paint them as text), a side that is not there at all (a file the run added or deleted) reads as empty, and a side that could not be read — a baseline the shadow repo no longer holds, a file the disk refuses — is reported as a failure rather than painted as a file with nothing on either side — while its `Undo` calls `undo_turn` to put the project back to that run's own baseline rather than the repository's last commit; a project need not be a git clone, since the snapshot repo is oxide's own, and where the snapshot is refused (the home directory, anything holding the config directory, a directory that is neither a git work tree nor project-sized) the turn simply leaves no card. Because that listing already holds the call's own diff, a tool card that changed a file reads as one line — path and `+`/`−` counts — and unfolds its diff when it is clicked, so the same change is not painted twice. The header names the open thread by the same summarized title its sidebar row shows — including a turn that is still running, whose title arrives with `agent-start` — and says beside it only what has to be acted on (`no API key`, `project resources off`), since the provider is already the composer's model chip; a thread the store has not written yet is listed all the same, since a listing that reads only what is on disk showed a running thread no row of its own: the thread the window is in stands in for itself — under the title the header shows, in the sidebar's tree, in that project's session count and in the `/sessions` list — keyed by the same id, so the store catching up to it replaces the row rather than adding a second one, with its own row handled in the window rather than by the commands that read a session off disk (its timestamps in the store's own Unix seconds, so its age is a number rather than `just now` forever; selecting it leaving the thread already on screen, title and all, as it is; and no ✕ offered, since there is no file to delete), and a window with no thread on screen starts one of its own with its next message rather than appending that message to whichever thread was used last; the composer's corner holds Stop while a turn runs with nothing to say, then Send beside a visible Queue/Steer choice when new context is typed — Queue is the safe default and waits for the current response, while Steer is the deliberate course correction injected before the next model step — the window is built with `acceptFirstMouse` (`tauri.conf.json`) and no AppKit event monitor or direct Objective-C dependency; the webview owns pointer and activation semantics, and every actionable control is wired to a plain `onclick` without a synthetic-click, focus, or press/repaint controller. A nested control stops its click from reaching the row around it, so a thread's ✕ removes the thread rather than selecting the row and a chip's ✕ removes the chip rather than opening the picture; a thumbnail needs its picture to stay undraggable (`draggable = false` and `-webkit-user-drag: none`) for the same reason, since a drag that starts on the image is the one gesture whose click WebKit withholds. the image preview is closed by the ✕ icon button its sibling dialogs carry, which sits in a head row above the picture — outside the image it closes, in the error color — rather than a text button. Assistant replies render Markdown as HTML, and both
inline and bare `http(s)` links open in the system browser through the `open_url`
command, since the webview cannot navigate to a remote page itself. A tool a
permission rule gates is asked about instead of run on trust:
the CLI's rpc mode and the extension broker it through `oxide_core::approval`, the
desktop through `crates/desktop/src/approval.rs` and the window's own event channel
(which emits `approval-request` and answers from `resolve_approval`), and the TUI asks in the
transcript and answers in the composer through the same broker. All of them
remember an **Always allow** in the same `oxide_core::approvals::ApprovalStore`
(`approvals.json`). A skill's question — the agent-level `ask` tool — travels to
the front-ends the same way and is answered only by the two that have a dialog
for it: the desktop through `crates/desktop/src/ask.rs` (which emits
`question-request` and answers from `resolve_question` with the labels picked
and the text typed, or nothing at all for a dismissed dialog) and the extension
through the CLI's `oxide_core::ask::AskBroker` over its rpc channel (`--ask-questions`,
answered with a `question` frame), while a TUI or print run is given no asker at
all, so `ask` is not offered there and the model never waits on a question nobody
can see. An unanswered question gives up after five minutes and the tool reports
that nobody answered, so a turn cannot hang; the request is then announced as
closed — `AgentEvent::QuestionClosed` in rpc mode, the desktop's own
`question-closed` — so a dialog is hidden rather than left offering an answer
nothing is waiting for, and a run that ends (or is stopped) takes its own
pending requests with it. The desktop's MCP list (`mcp_servers`, `set_mcp_server`) and
its `/` palette (`list_commands`) read the same core the terminal does —
`oxide_core::mcp_config::server_views` and `oxide_core::commands::palette` — and
a row of that palette is taken to complete the composer rather than run it,
since a command, a prompt template and a skill all take the arguments they are
sent with: a skill is listed under its own name (its row badged `skill` beside
its description), so `/name` is what the app puts in the box and the CLI is what
resolves it, while `/mcps` in its composer opens that list instead of sending
the text to the model, and `/sessions` (alias `/session`, with an argument left
to the agent) opens a **Sessions** list over `all_sessions` — the project's threads, newest
first, each row resuming one — so the list the sidebar groups by project is also
reachable from the composer, as the terminal's `/resume` picker and the
extension's listing are. Either is a panel of the composer's own column rather
than a window over the app (`ui/index.html` places both inside `.composer-wrap`,
above `.composer`), so each grows upward from the composer's top edge, stays
attached to it, keeps the transcript readable behind it, and scrolls its own rows
once the list is longer than the space it takes; its buttons are icon-only — a
power switch per server and a plus and a close in each header, each with the
words in its tooltip — the same treatment the extension's two listings get. Both
commands refuse an empty project path rather than resolving it to
the process's own working directory, so the list and the switch always act on
the project the window shows, and `crates/desktop/check-app.mjs` drives
`ui/app.js` against a stubbed DOM and a stubbed Tauri bridge (the `/mcps` list, the
switch, the `/sessions` list and its resume, the Add-project dialog, the
attachment chips — an image's thumbnail and
the full-size preview it opens — the one line an edit's card reads as and the
`@` completion's rows, keys and splice, and
every client command in the catalog, plus a
read of `index.html` for both listings' attachment to the composer, the `@`
list's own box and their icon-only buttons, and the question dialog: its rows,
the title the first
question gives it, the step counter and dashes, `Next` walking on with `Back`
returning to what an earlier step kept, the empty answers a blank form and Dismiss
both send, and the
request that closes it, whether the run ended or the CLI gave up on it) because
no Rust test runs the app's JavaScript, while `crates/desktop/check-shell.mjs`
joins the two halves the stubs separate — every command the page performs
answered by an arm in `src/commands.rs`, the events `commands.rs`, `approval.rs`,
`ask.rs` and `turn.rs` emit exactly the events `app.js` listens for, the
`oxide_invoke` command `src/main.rs` registers and the dispatcher behind it, the
CSP left to the window rather than the page, the capability naming only the
window `tauri.conf.json` opens and granting it nothing beyond `core:default`,
the bundle's icons on disk, and nothing left of the shell Tauri replaced. Its **+ New** button asks for a folder
through the window's native dialog (`pick_folder`, the Tauri dialog plugin), so the macOS
chooser is a panel of the app rather than a helper process launched from a
non-interactive one, and `DesktopManager::load_lossy` backs up an unreadable
`projects.json` instead of bringing the window down with it (`oxide_core::workspaces`
resolves the registry path from the same definition, so the file the sidebar
writes is the one a turn is told about). A turn that
finishes raises the same desktop toast the TUI does (`oxide_core::notify`, gated
by the shared `notifyOnComplete`/`notifySound` settings), named by
`turn::notify_finished` after the thread's summarized title — the session's
name, else its `preview` of the first thing sent, the label the sidebar shows it
under — and skipped for a turn the user stopped themselves. **Check for Updates…** is the app's own release train wearing a dialog: the macOS app-menu item (directly under **About**) asks the window through `check-updates` to run what the sidebar footer's **↻** button runs, `crates/desktop/src/update.rs` resolves the newest `desktop-v*` release for this platform through the shared `oxide_core::updates` (the same rules `oxide update` and the VS Code panel use, so the app offers a desktop release and never the CLI's own newest tag), and the dialog reports the version the app runs, the tag, the installation it found and its path, offers **Install** only when this copy can be written over from inside the app (an app bundle, an AppImage, a Windows installer — not a distribution package, a checkout's build, or a copy an administrator put in place for every user, each of which is given the file to install by hand instead), and opens the release page through `open_url`; the install re-resolves at the click, verifies the download against the SHA-256 GitHub reports for the asset, and puts it in place the way this copy was installed (mounting the `.dmg` and staging the `.app` beside the installed one before renaming it over, writing an AppImage over its own file, or launching the Windows installer), reporting the path it landed at and the one thing left to do — quit and open the app again; the dialog is owned by the newest check (`updateProbe`), so an answer the menu and the sidebar's **↻** asked for twice cannot repaint it with the older release. The published CLI keeps its own train: `oxide update` replaces that binary, through the same shared resolution with `--component cli`.

- `crates/cli/src/main.rs` — CLI entry (clap). Non-interactive `-p/--print`, `--mode json`, and `--mode rpc` modes plus TUI dispatch; the `mcp`, `sessions`, `plugin` (including `plugin marketplace`), `commands`, `update`, and `uninstall` subcommands. `sessions show <id>` prints one saved conversation (`--tail <n>` for its newest messages, `--json` for the object a front-end draws), which is how a client shows the thread it is about to resume without agreeing with the core on the session layout; `mcp list --json` prints the serializable `ServerView` listing a front-end draws and `mcp disable|enable <name>` flips a server's `enabled` in the file that defines it (or in a pinned `--scope`) without deleting its configuration, and `commands --json` prints the slash-command catalog the desktop's `/` palette is built from (`oxide_core::commands`). `changes show <path> --baseline <rev> [--project <dir>]` prints one file as that run's baseline recorded it, out of the project's shadow snapshot (`--project` defaults to the working directory), which is how a front-end that draws its own diff reads the one side that is nowhere on disk. `changes undo --baseline <rev> [--after <rev>] [--project <dir>]` puts that run's files back through the same core restore the desktop app's Undo and the terminal's `/undo` perform, refusing with the reason an `--after` the work tree has moved past, so a front-end that cannot link `oxide-core` can still offer its card an Undo, and `update --check --json` prints the check such a front-end draws — the release the CLI resolved, what this installation is, whether `oxide update` may replace it and the CLI's own advice — while a CLI older than the caller that does not know the flag says so, which is what the desktop app and the VS Code panel report instead of a failed check. Provider login is TUI-only (`/login`, `/logout`), matching Pi. `--ask-approvals`/`--no-ask-approvals` decide whether a permission-gated tool is asked about: in the TUI the question is answered in the composer, and in rpc mode the turn emits `approval_request` and waits for the client's `approval` frame (which is why `--mode rpc` is the mode the VS Code extension runs). Either flag switches `auto_approve` off or on for that run, and because `-p`/`--mode json` have no channel to answer on they reject both rather than silently running the tool they were meant to gate. An rpc turn is marked against the project's shadow snapshot when its prompt arrives (`mark_baseline`), and a run that finishes having changed something hands the client a `turn_changes` control frame — the baseline revision and the listing, from `Snapshots::changes_since` — ahead of that run's `agent_end`, so a client can show what the turn changed and diff a file against the state it found. `--ask-questions` is the same bargain for the `ask` tool — a skill's question — and is rpc-mode only: without it no asker is wired in, so `ask` is not offered at all and therefore never asks a question the caller cannot answer, and any other mode rejects the flag.
- `crates/core/src/mcp_config.rs` — `oxide mcp add/list/get/add-json/remove/auth/disable/enable`: reads and writes MCP servers in the native `.oxide/mcp.json` files (`--scope project|global`), merging sources for listing in the same precedence the runtime loads (Claude Code global, `~/.oxide`, the platform config dir, then the project), with a global file reported once as global when the project root resolves to the home directory; `auth`, `remove`, `disable` and `enable` keep a pinned `--scope` inside that scope's files in both layouts (`--scope project` covers a Claude Code `.mcp.json` as well as `.oxide/mcp.json`, so a name defined in both scopes resolves to the requested one), while an unpinned command searches every source in precedence order. `disable`/`enable` write both spellings — `enabled`, and Claude Code's `disabled` kept in step (written when turning a server off, dropped when turning it on) — so the file says the same thing to a harness that reads either one, and a server can be turned off without losing its configuration; a name whose entry is not an object, or that is nowhere while a source cannot be parsed, is reported instead of being passed over or written elsewhere. `mcp list --json` prints a `ServerView` per server — name, transport, detail (URL or command line), the `source` file's label, the `scope` (`project`/`global`) a toggle should pin to, `enabled`, the machine-readable `state` from `McpStatus::state()` (`connected`/`needs-auth`/`needs-trust`/`disabled`/`error`) and its display `status` — which is what the desktop dialog and the extension's `/mcps` dialog draw; `server_views(cwd)` is the same listing for an in-process caller, and `set_enabled` the same toggle. A disabled server reports `disabled` wherever it lives, and a project's servers report `needs-trust` until the project is trusted rather than being started. `add` also accepts the Claude Code-style `oauth` fields (`--oauth-client-id`, `--oauth-client-secret`, `--callback-port`, `--oauth-scope`, `--redirect-uri`).
- `crates/core/src/commands.rs` — the shared slash-command catalog: the built-in client commands with their aliases, descriptions, fixed argument grammars and a `Kind` (`client` for a command a front-end performs itself, `prompt` for one it runs by sending `/name args`, `skill` for a configured skill, which is listed under its own name — sending `/name` loads it, and `/skill:<name>` is the terminal's other spelling, kept as an alias), plus the commands, prompt templates and skills the project (and its plugins) contribute, discovered through `crate::ecosystem`. An agent contributes no entry — it is not a slash command but a subagent a front-end selects with its own picker (`/agent` in the terminal, `--agent` for a run), and a command whose frontmatter declares `agent`/`subtask` routing is an ordinary `prompt` entry the CLI routes when it runs it, so a client only sends the prompt. `palette(root)` is what the desktop's `/` palette draws, `builtin(name)` resolves a name or alias, and `list(root, json)` backs `oxide commands`. The desktop app reads `palette` and the TUI keeps its own built-in list, so a name a front-end answers itself is still declared here once.
- `crates/core/src/config.rs` — `Config` struct; loads `config.json` from the Oxide config dir (`dirs::config_dir()/Oxide`, e.g. `~/.config/Oxide` on Linux, `~/Library/Application Support/Oxide` on macOS) plus `OXIDE_*` / provider env overrides. Provider presets cover OpenAI/GPT, DeepSeek, Anthropic, Portkey, and Z.AI/GLM (`OPENAI_API_KEY`, `DEEPSEEK_API_KEY`, `ANTHROPIC_API_KEY`, `PORTKEY_API_KEY`, `ZAI_API_KEY`); Portkey also supports custom gateways/config IDs and model catalogs, and Z.AI is the second provider with a bundled catalog (`GLM_FALLBACK_MODELS`) for `/models`. Defines the `Reasoning` enum (`auto` / `off` / `low` / `medium` / `high`, set via `--reasoning`, `OXIDE_REASONING`, or config), composes the system prompt (a `# Definition of Done` section that forbids reporting unobserved work and requires confirming the outcome of any state-changing action — edits/builds, pull requests, comments and reviews, releases, deployments — before claiming success, while letting an explicit instruction from the user outrank every one of those checks — a "no need to check the PR's status" is followed and the reply says plainly what was left unverified rather than the check being run anyway and holds a review fix until it is committed and pushed before the reply in the thread, a `# Scope` section that keeps commits and PRs limited to the paths the task touched and forbids blanket staging, tool-use guidance that steers toward the dedicated `read`/`grep`/`find`/`ls` tools over compound shell commands (including codebase searches, which a repo-root shell `grep -r` runs through build output and `.git/` while the tools skip both and honor `.gitignore`), and the loaded ecosystem — listing skills, commands and subagents for model auto-invocation, plus a `# Plugins` section naming every plugin the run knows about with the description and the capabilities it brought (`2 skills, 1 command, 1 MCP server`), one marked `(disabled)` when it is installed but switched off, and how many hook plugins are active, so a request that belongs to a plugin is met with what it provides instead of the model building a workaround or telling the user to install a plugin that is already there), resolves `/commands` (including `agent`/`subtask` routing and a skill by its own `/name`, with `/skill:<name>` kept as the terminal's alias), and loads context-compaction config from `settings.json` and `.oxide/settings.json`. Switching providers remembers the model and custom endpoint last used with each one (`provider_models` and `provider_base_urls` in `config.json`, with the active provider's endpoint mirrored to `base_url`) so each login keeps its own model and gateway, and `for_provider` builds a copy of the config pointed at another logged-in provider for catalog queries. `Config::load` also reads the local projects (`crate::workspaces`) into the `# Workspaces` section, so the composed prompt names this run's directory and the other folders added to Oxide, and the `# Tool use` guidance forbids a `find ~` sweep as well as `find /`.
- `crates/core/src/auth.rs` — stores provider API keys/tokens for any number of providers side by side in `auth.json` in the Oxide config dir (mode 0600); keys are resolved after env vars and before the config file. Authentication is TUI-only (`/login`, `/logout`), matching Pi: `connect` also writes the active provider to `config.json` so the next launch uses it, `select_stored` adopts a provider that is already saved so switching between logged-in providers never asks for the key again, and `stored_providers` lists them. `canonical_provider` maps aliases onto the preset names (`gpt`/`gpt-4o` → `openai`, `port-key` → `portkey`, `glm`/`z.ai`/`zhipu`/`bigmodel` → `zai`). There is no `oxide auth` subcommand.
- `crates/core/src/ecosystem/` — discovers and loads configuration from project and global scope: the native Oxide layout (`.oxide/`, `AGENTS.md`, `.oxide/mcp.json`) plus the Claude Code layout (`.claude/`, `CLAUDE.md`, `.mcp.json`) for compatibility. Context files (`AGENTS.md`/`CLAUDE.md`, with `AGENTS.override.md` replacing its directory) are collected by walking every ancestor directory down to `cwd`, and `.oxide/SYSTEM.md`/`APPEND_SYSTEM.md` replace or extend the system prompt. Covers instructions, commands, prompt templates (`prompts/*.md` with Pi-style argument expansion), agents/subagents, skills (`SKILL.md`), MCP servers and plugins. Installed plugin packages contribute their `commands/`, `agents/`, `skills/`, and MCP servers — read from the manifest `mcpServers` or a plugin-root `.mcp.json` in either the wrapped or bare-map form — and each loaded plugin is recorded as a `PluginSummary` alongside the counts of what it contributed, so the prompt can describe it by what it shipped; a plugin that is installed but disabled is recorded too (without contributing anything), so a request it answers is not met with a workaround or a fresh install. Project-scope resources are gated behind project trust via `ecosystem::load_opts`. This repository keeps its own agents, commands, prompts, skills and plugins in `.oxide/`; user-facing configuration guidance lives in `docs/cli.md` (task guides) and `docs/configuration.md` (reference tables).
- `crates/core/src/trust.rs` — project trust: `TrustStore` persists per-directory decisions in `trust.json` (closest ancestor wins), `requires_trust` detects project-local resources, `resolve` applies the CLI override plus `defaultProjectTrust` (read from `settings.json`), and untrusted projects reload without project resources (context files still load).
- `crates/core/src/workspaces.rs` — the local projects a run is told about: reads the desktop's project registry (`desktop/projects.json`, the folders added in the app), keeps the ones that still exist and are not the run's own directory (the run's directory is resolved to its absolute, filesystem-resolved form first, so a relative `-C .` is recognized as the project the desktop recorded rather than listed beside itself), and orders them with the current project's sibling first and then by most recently opened (capped at `MAX_LISTED`, the rest counted), so `Workspaces::section()` can name this run's directory and every other project Oxide knows with its path in a `# Workspaces` section of the system prompt. That is what answers "can you reach the `<repo>` repo?" and what says the file tools take absolute paths — a file in a sibling project is readable, searchable and editable from the run, while `bash` still starts in the current project's root — so the model resolves a repository from the list rather than a `find ~` that reads every unrelated file on the machine until the command times out. A registry that is missing, unreadable or malformed leaves a run knowing nothing but its own directory, and `Config::load` reads it once per run so the CLI, the desktop app and the VS Code panel are told the same thing.
- `crates/cli/src/theme.rs` — semantic TUI color themes: built-in `dark`/`light` (built from `oxide_core::theme_view` so they match the desktop), custom `.oxide/themes/<name>.json` (color names or `#rrggbb`), selected with `--use-theme` or `/theme`. Slots cover focus, speakers, success, tools, errors, supporting text, borders, tool panel backgrounds (`tool_pending_bg`/`tool_success_bg`/`tool_error_bg`), the Portkey spend bar (`usage_bar_bg`/`usage_bar_fg`/`usage_bar_label`), thinking levels, and `thinking_text` for reasoning blocks.
- `crates/core/src/agent.rs` — agent loop: stream the model, execute requested tools, and feed results back until the model stops calling tools or a batch reports `terminate`. Read-only tool calls in a batch run in parallel (results kept in call order) while mutating tools stay sequential; a `Steering` queue injects user messages typed mid-run before the next model call, and a batch whose results all set `terminate` ends the turn. Hosts the agent-level `task` (subagent), `skill` (on-demand load), `command` (model-invoked commands/prompt templates; `subtask` commands run as subagents), `memory`, `diagnostics`, and `ask` tools; `run` returns a boxed future so subagents can recurse (capped by `MAX_TASK_DEPTH`), and `run_subagent` runs a `subtask` command in an isolated context. A `Runtime` bundles the MCP registry, plugin host, session log, snapshots, LSP manager, the steering and follow-up queues, and the approval callback. Provider-reported token usage (input/output, cache tokens, and cost) is forwarded as `AgentEvent::Usage`, `ThinkingDelta` forwards streamed reasoning and `Retrying` a transient failure about to be retried (the failed attempt's partial text is dropped, and the last attempt's text is recorded to the session when the retry budget is exhausted), `SubagentActivity` carries a nested subagent's tool call up to the originating view (the `task` tool otherwise emits nothing until it returns), and auto-compaction appends a `compaction` entry to the session branch. A `VerificationState` tracks files edited in a run until each is read back, inspected from the shell (a `git diff`/`git show`/`grep` naming the file confirms just that file) or covered by a build/test/lint command, and a table of `DONE_RULES` covers side effects that outlive the workspace (`gh pr create`/`glab mr create`, comments and reviews, releases, deployments and publishes) until a matching status command reads their outcome; if the model tries to finish with any unconfirmed it gets one hidden system reminder (a `# Definition of Done` note) to verify before summarizing (the reminder repeats that a user instruction to skip a check outranks it), and a provider that answers that reminder with no answer ends the run with the summary already in hand instead of surfacing `the model returned an empty response` on top of a complete reply — while a non-empty answer is merged into the summary it re-checked (text and usage together, the step held open so the transcript paints one bubble) so a re-checked run ends with one summary instead of two. A `scope` rule flags blanket staging (`git add -A`/`--all`/`.`/`:/`, `git commit -a`) until a `git status`/`git diff --staged`/`git show` review confirms what is staged. A review reply that ships an edit stays unconfirmed until `git push` delivers it, so a fix left uncommitted while a review is answered is not reported as addressed; a review reply in a comment's own thread (a POST to the `/replies` endpoint) or a top-level comment (`gh pr comment`/`review`, `glab mr note`) is held while the repository has tracked modifications or unpushed commits (which also covers shell edits like `sed -i` or a formatter), so the thread is not answered before the branch has the fix — while an edit outside the repository the run works in (a scratch file, the body of the reply itself, a report under the home directory) is not part of that delivery and holds nothing, since it is not on any branch, and both halves of the guard judge an edit against the same boundary: the repository the run works in, found the way git finds it (the closest enclosing `.git`), so an edit beside a run that started in a subdirectory is the tracked modification `git status` reports rather than a file written outside the project; a single-branch clone's missing remote-tracking ref is resolved by asking the remote for the branch tip with `git ls-remote` (and accepting a tip the local commit is an ancestor of), so a fix that was actually pushed is not held forever. A repeated build/test command in the same run is flagged with a note rather than silently re-run.
- `crates/core/src/llm/` — model client. `client.rs` dispatches by provider: OpenAI-compatible chat completions (OpenAI, DeepSeek, Portkey, Z.AI/GLM, custom) and the Anthropic Messages API (`anthropic.rs`, converting internal messages to content blocks and parsing its SSE events, and marking the system prompt, the last tool, and the newest message with `cache_control: {"type":"ephemeral"}` so each turn reuses the cached prefix instead of re-reading the whole conversation; the OpenAI-compatible path sends the session id as `prompt_cache_key` for direct OpenAI and as `x-session-id`/`x-client-request-id` headers for gateways, so those providers also get cache affinity, and on a Claude model behind a non-OpenAI endpoint it translates the same Anthropic `cache_control` breakpoints into the OpenAI-shaped request so Portkey/OpenRouter can cache the prefix). Applies the configured reasoning level: OpenAI-compatible `reasoning_effort` and Anthropic adaptive or extended thinking, with Anthropic thinking blocks replayed on later turns and every DeepSeek assistant message carrying `reasoning_content` (its thinking mode answers a request that drops an earlier turn's reasoning — tool call or plain answer alike — with a 400, since the request carries tools, and `deepseek-flash` thinks nothing on quick tool calls and short answers, so the field is sent empty rather than omitted; `Config::is_deepseek` matches the provider, the first-party endpoint, and a DeepSeek model behind a gateway); GLM instead toggles `thinking.type` and maps levels onto its own `low`/`high`/`max` scale, asking forced-thinking models (GLM-5.3 and later, via `glm_forces_thinking`) for the lowest effort because they reject `disabled`. Streaming goes through `StreamHooks` (`text`, `thinking`, `retry`) so the caller can show work in progress: reasoning deltas (`reasoning_content`/`reasoning`/`reasoning_text`, normalized by `Delta::reasoning`) are merged into one Anthropic-shaped `thinking` block and forwarded as `AgentEvent::ThinkingDelta`; `types::push_thinking` grows that block in place by mutating its `Value::String`, since rebuilding the block per fragment would copy the whole trace and make a long reasoning stream quadratic, and `types::set_thinking_signature` records the signature Anthropic attaches to it. `read_sse` splits the byte stream with `drain_lines`, which hands each complete line to the caller and compacts the buffer once per chunk instead of after every line. A stream that drops without a TLS `close_notify` is remembered as an abrupt end: a turn whose sentinel or stop reason already arrived is returned, but an abrupt close before either is still an incomplete (retryable) turn rather than a partial success, and a plain truncated body is still an error. A retryable failure emits `Retry { attempt, max, delay }` before backing off; a retry may follow an attempt that already streamed text or reasoning, so each front-end drops the assistant or thinking item still in progress when it sees the retry, and the retry streams fresh instead of extending the partial output. `stream_chat` retries transient failures (network errors, truncated streams, 429/5xx) with backoff, retries a turn that carries neither text nor tool calls (`assistant_turn_is_empty`), and only turns empty/truncated streams or in-band `error` payloads into errors once the retry budget is exhausted; an empty or reasoning-truncated turn is reported as the downcastable `NoAnswer` error so a caller that sent a best-effort request can tell it apart from a real failure. A turn whose provider stop reason is the output limit (`finish_reason`/`stop_reason` `length`/`max_tokens`, captured on `AssistantTurn`) instead retries with a doubled `max_tokens` up to 32768, since a reasoning model that spent the whole budget thinking would only truncate again at the same cap. The Anthropic path shares the empty-turn check and treats a `message_delta` stop reason as completion, so a dropped stream is retried instead of returned as an empty turn. Both wire paths repair the outgoing history before serializing it (`repair_tool_pairs`): an assistant tool-call turn stored without its results (a run killed mid-tool, a truncated log) gets a result the provider accepts, and a tool result whose call is gone is dropped, so a 400 (`An assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'`) does not fail every later request against the same broken log.
- `crates/core/src/mcp.rs` — MCP runtime: connects configured servers over stdio or HTTP, initializes JSON-RPC sessions, and exposes remote tools (`<server>__<tool>`). Remote servers with an `oauth` block attach a bearer token per request. Servers stay lazy — nothing is started or requested until one is needed — but a user message that names a service selects the server configured for it the same way a pasted URL does: `servers_for_text` matches the words of a server's own name, the aliases of the well-known service its name belongs to, and the service its configured URL or command points at (`company-tools` at `mcp.atlassian.com` answers to `confluence`/`jira`), so "create a Confluence doc" loads the server before the first model call instead of leaving the model to ask for a URL, while words too short or too generic to name a service are ignored; `McpServer::domains()`/`service_names()` derive the same identities, so such a server also owns its service's URLs and `mcp_load` — whose schema lists every name a server answers to — loads it by any of them, reporting a name more than one server answers to rather than guessing. A server's own `instructions` from the initialize handshake are kept and passed to the model — in the `mcp_load` result when the model loads it, and as an `# MCP server notes (untrusted)` section of the system prompt from `instructions_section` for the rest of the run — so guidance like "call getAccessibleAtlassianResources first" reaches the model even when the server was auto-loaded rather than asked for; that section says the text came from the servers themselves rather than the user or the policy and cannot change the instructions above it, grant a permission or redirect the task, since a third-party server's text must not read as policy. Connecting never logs in: a server whose token is missing (or too stale to refresh) fails with `AuthorizationRequired`, which names `oxide mcp auth <name>` so the model asks the user to authorize out of band instead of retrying, and `/mcps` repeats that on the row it marks `Needs Auth`. Authorization opens a browser and then waits on the loopback callback for up to five minutes, so a turn that started it would strand the run behind a login the front-end cannot show — `load` used to hand `stdin().is_terminal()` to the OAuth state as an "interactive" flag, which made the TUI, the one front-end whose stdin *is* a terminal, the one place that happened. A refresh needs no browser and still runs mid-turn, so an expiring token is invisible.
- `crates/core/src/mcp_oauth.rs` — OAuth 2.0 authorization-code + PKCE for remote MCP servers: metadata discovery, loopback callback, token exchange/refresh, and `mcp-oauth/<server>.json` storage (mode 0600). `ensure_authorized` is the interactive flow and belongs to `oxide mcp auth <name>` alone — a command the user is waiting on; an agent run asks `access_token_if_available`, which refreshes silently and otherwise reports nothing rather than opening a browser. The callback answers with a self-contained branded page (semantic color tokens, light and dark via `prefers-color-scheme`, status icon, headline, message naming the server, a monospace block for the provider's error detail, a best-effort `window.close()` after success, all text HTML-escaped, no external assets) plus `Cache-Control: no-store`.
- `crates/core/src/at.rs` — the `@path` completion's rules, held once so a reference completes identically in the terminal's composer and the desktop app's (the VS Code panel cannot link the crate and mirrors them in `editors/vscode/src/core/at.ts`): `token(value, caret)` reads the reference the caret sits in — a word-boundary `@` running to the next whitespace, so an address names no file, and the whole token even when the caret is inside it — and `suggestions(paths, token, max)` ranks the workspace listing its caller supplies (`tools::workspace_paths`, gitignore-aware, files and their parent folders) into rows, case-insensitively: a name that starts with the query, then the whole path that does, then one that mentions it anywhere, capped at `MAX_AT_SUGGESTIONS` (200). A folder's row inserts `@dir/` and keeps the reference open, a file's inserts `@file ` and closes it, and a folder the reference already spells exactly is left out, so taking a row walks *into* that folder instead of completing it to what is already typed.
- `crates/core/src/media.rs` — multimodal attachments: dependency-free base64 (`base64_encode`/`base64_decode`), image/PDF MIME detection, `@path` reference extraction, and a best-effort OS clipboard grab. `clipboard_attachment` prefers a file the clipboard holds over its picture — a Finder copy puts the file URL *and* the file's icon on the pasteboard, so the image grab attached a copied screenshot as a `PNG`-document icon; this is macOS-specific, as a Linux or Windows file copy carries no picture to mistake for the file; a file that is here but cannot be attached is reported instead of replaced by that icon, while a path this machine does not have (a screenshot or a file copy that arrived from another one, whose URL travelled with the pasteboard but whose file did not) is left to the pasteboard's own image rather than reported as nothing to attach. The macOS file URL is read out of `NSPasteboard` (AppKit's `readObjectsForClasses:{NSURL}` with `isFileURL`), not by coercing the clipboard with AppleScript's `«class furl»`, which turns any text into a path (`/plain text`, `/https/::host/photo.png`) and only inspects the first pasteboard item — so an icon listed ahead of the file URL failed the coercion and fell through to the icon; reading the real URLs finds the file wherever it sits and answers nothing when there is none. The image itself is read the same way (`dataForType:` for `public.png`, then the `public.tiff` a copy from Preview or Safari leaves, converted with `sips`), which asks the item for the type it advertises instead of coercing it — what `pngpaste` does, and the read that fetches a pasteboard whose bytes are not on this machine yet — and it is asked before `pngpaste` (`-`, when it is installed) and the coercing AppleScript, which are then answers for a machine where that read found nothing (`wl-paste`/`xclip` on Linux). `optimize_image` downscales an oversized PNG/JPEG/WebP (long edge 1568, dimensions parsed from the header) with `sips` on macOS or ImageMagick/ffmpeg on Linux in a private randomly named temp directory that is removed on drop, falling back to the original, so a pasted screenshot is not base64-encoded and stored at full resolution; `content_part_from_data_url` turns a desktop data URL back into an image/PDF part and downscales it the same way (a GIF is left alone so an animation is not flattened), since a data URL never touches a path and is otherwise the one attachment that could stay at full resolution. `MAX_ATTACHMENT_BYTES` (20 MB) bounds an attachment on both routes — `load_attachment` checks the file's length before reading it and `content_part_from_data_url` checks the data URL's decoded size before keeping it — `MAX_DATA_URL_CHARS` is the base64 length of a full-size payload, so a URL at the limit decodes to fewer bytes than `MAX_ATTACHMENT_BYTES` and an image is measured again after decoding — because the bytes exist several times over at once (the front-end's copy, the IPC message, the session entry, the request body), and `is_supported_image_mime` is the set a provider takes *and* a webview can paint, so a TIFF is refused rather than sent or drawn as a thumbnail that cannot render. Both return `None`/an error for a refused attachment rather than dropping it silently.
- `crates/core/src/clipboard.rs` — system clipboard writes for the TUI: always emits an OSC 52 sequence (wrapped in a DCS passthrough under tmux/screen, so copies survive SSH) and additionally tries a native helper (`pbcopy`/`osascript`, `wl-copy`/`xclip`/`xsel`). A copy reports itself with a dim `ChatItem::Status` tip, since `App.status` only renders while the agent is busy.
- `crates/core/src/memory.rs` — persistent cross-session memory store (project + user scope) under `memory/` in the Oxide config dir, with dependency-free tf-idf search.
- `crates/core/src/notice.rs` — out-of-band notices from the core to whatever front-end is running: the things that belong to no tool call and no `AgentEvent` — an MCP server's OAuth flow naming the URL it opened, a plugin runtime that would not start or a plugin package that was skipped, an approval rule that could not be saved. A front-end installs a `NoticeSink` once (`set_sink`, first caller wins, since the first one to claim the screen owns it) and `info`/`warn` route a `Notice` (its `Level` and text) to it; with no sink installed — a `-p`/`--mode json`/`--mode rpc` run, whose stdout is reserved for frames — the text falls back to stderr. That is what keeps these messages off the TUI's alternate screen: ratatui only rewrites cells whose style changed, so a raw `eprintln!` from the core landed as garbled text no later frame repainted, which is why nothing in `crates/core` prints to stderr directly anymore. The TUI takes the sink's notices on a channel of its own in `event_loop` and pushes each one as a `ChatItem::Info` (or `ChatItem::Error` for a `Warn`) with `auto_scroll`, so an authorization URL is a transcript line the reader can scroll back to.
- `crates/core/src/notify.rs` — best-effort desktop toast for a completed agent turn: `send` runs the platform notifier on a detached thread (Notification Center via `osascript` on macOS, `notify-send` plus the freedesktop `complete` sound via `canberra-gtk-play`/`paplay`/`aplay`/`ffplay` on Linux, a WinRT toast with `Notification.Default` audio on Windows). `load_config` resolves `notifyOnComplete` and `notifySound` from the global and project `settings.json` (project wins per key) with `OXIDE_NOTIFY_ON_COMPLETE`/`OXIDE_NOTIFY_SOUND` overrides; both default on; the VS Code panel reads `notifyOnComplete` the same way next to its own `oxide.notifyOnFinish`, so turning notifications off in the terminal silences it too (a VS Code notification carries no sound of its own, so `notifySound` is the CLI's and the desktop's). The TUI `/notify [on|off]`, `/notify sound [on|off]`, and `/notify test` commands mutate the running config and persist the flags to the global `settings.json` through `save` (`OXIDE_SETTINGS_FILE` overrides the path). The TUI only toasts for real agent runs (internal work like `/compact` and branch summaries sets no `App.notify_on_finish`), using a short title pulled from the newest assistant reply (its first non-empty line, with Markdown markers stripped) as the body instead of the whole summary.
- `crates/core/src/session.rs` — Pi-compatible session storage under `sessions/<project>/` in the Oxide config dir. Each file is a JSONL tree: a `session` header followed by `message`, `compaction`, `branch_summary`, `session_info`, `model_change`, and `thinking_level_change` entries carrying `id`/`parentId`/`timestamp`. The last entry is the active leaf; appending adds a child of the leaf, `branch_with_summary` moves the leaf and appends a branch summary, and `context`/`messages` walk the leaf path with the latest compaction applied. A session's `preview` is its first user message summarized by the shared title rules (`crate::title`), so a picker row, the desktop's sidebar and the panel's header agree. Sessions are resumed via `-c/--continue`, `-r/--resume` (session picker), `--session <path|id>`, or `/resume`; `list` returns picker summaries (id, name, preview, message count), `delete`/`rename` manage sessions, `rewrite` rewrites a session as a linear chain, and `fork` seeds a new session from a message slice (used by `--fork`, `/fork` and `/clone`). Appends are fsynced and recover from a partial trailing line; an append to a file that was removed underneath a running session — a delete from another front-end — rewrites the header and every in-memory entry first, so the live conversation continues instead of failing with `No such file or directory`. Reading is cycle-safe: a corrupt file whose entries form a parent/child loop (or whose newest entry points at itself) is walked with a visited set, so `list`, `summary` and `context` terminate instead of spinning — a hang there used to look like a frozen app, since the desktop's sidebar and the CLI's session picker both walk every file. `new_id` mixes the full nanosecond clock into a 64-bit value, so two sessions created in the same millisecond do not collide. Resolving an id to its file is done by name (`<millis>_<id>.jsonl`, with a stem suffix accepted), so resuming a thread in a project whose store holds many sessions — or one 37 MB thread — reads that file instead of parsing every other session to find it, while a file that was renamed still resolves through the header of its first line.
- `crates/core/src/sessions.rs` — non-interactive session management (`oxide sessions list/show/delete/compact/merge`) for stale-session cleanup; `show` prints one session's conversation (the leaf path with the latest compaction applied) as text or as the JSON a front-end draws — id, name, cwd, path, the number of messages in context, how many of them were returned, the messages with their tool calls, and the thread's usage totals — which is what the VS Code panel replays when it resumes a thread; `delete` filters by id/`--all`/`--older-than`, `compact` summarizes older history into a summary plus recent tail (one LLM pass per session), and `merge` concatenates two sessions or summarizes the second one first.
- `crates/core/src/title.rs` — the one-line title rules every front-end names a thread, a session and a finished turn by: the first line that reads as prose (skipping blank lines, a fenced block's contents, a table row and a line that is only punctuation), with its Markdown taken off (`#`/`>`/`-`/`1.` markers, emphasis, code, and a link or image reduced to its text) and collapsed, then cut to `TITLE_LIMIT` (64) at a word boundary with an ellipsis. `session::preview_text` (what a session is listed under when it was never named) and the TUI's completion toast use it, so the desktop's sidebar and toast, the terminal's picker and toast, and the VS Code panel's header all say the same thing about the same conversation; the panel is TypeScript and cannot link the crate, so `summarizeTitle` in `editors/vscode/src/core/protocol.ts` mirrors the rules and `test/protocol.test.ts` holds the same cases as this module's tests.
- `crates/core/src/snapshots.rs` — shadow-git snapshots (bare repo under `snapshots/<project>/` in the Oxide config dir) committed after each agent step; `/undo` and `/redo` in the TUI restore file changes. `baseline(&cwd)` records the state a run starts from and returns the revision to compare against, `changes_since(base)` lists the files that changed since it (what the desktop's change card, the VS Code panel's card and `oxide changes show` all read), `content_at(revision, path)` reads a file as that revision recorded it — the left side of a diff, which is nowhere on disk — and `restore_turn(base, after)` puts the work tree back to it, refusing (with the reason) when `after` names a state the tree has moved past, so an older run's restore cannot take a newer one's work with it — the one path behind the desktop's `undo_turn`, the terminal's `/undo` and the extension's `oxide changes undo` (`restore(base)` is the same reset without the guard). A project does not have to be a git clone: the shadow repo is oxide's own, so a plain folder is recorded too, and what `snapshot_scope_is_safe` refuses is only what must not be walked — the volume root, the home directory or an ancestor of it, a directory holding the config directory (which holds the shadow repos themselves), and a directory that is neither inside a git work tree nor project-sized (`EXCLUDED_DIRS`' build output and dependency trees left out of the count), so a turn in a folder that is not a project leaves no listing rather than indexing a whole disk. Everywhere else a git work tree is trusted as it stands, since its own `.gitignore` is what bounds `git add -A`.
- `crates/core/src/changes.rs` — the files a run changed, as a front-end lists them: `ChangeStatus` (`Added`/`Modified`/`Deleted`, with the `A`/`M`/`D` `letter()`), `FileChange` (path, status, the added/removed line counts, `binary`, and the same compact line-numbered preview `crate::diff` renders for a single edit), `TurnChanges` with the totals a card's header shows, and `empty()`. Everything is pure — `parse_name_status` reads `git diff --name-status -z` (a rename's new name is the file to show, since git reports both), `count` reads the `+`/`-` a preview line starts with, and `summarize` adds the entries up — while the git-facing half is `Snapshots::changes_since`, so a file no tool call named is listed the same as an edited one and a file a run deleted reads as deleted rather than as an unstaged removal.
- `crates/core/src/permission.rs` — parses per-agent `permission` rules into allow/ask/deny and decides per tool + subject; `ask` prompts in the TUI unless `auto_approve` is set (the `config.json` key `/approvals on|off` flips), and a `deny` rule reaches an interactive approver instead of denying outright.
- `crates/core/src/approval.rs` — the interactive tool-approval broker shared by the CLI's rpc mode, the TUI and the desktop app: an `Approver` callback that emits `AgentEvent::ApprovalRequest { id, tool, detail }` and awaits the answer for that id — `ApprovalBroker::resolve` for a front-end that has a wire word (`deny`/`once`/`always`, parsed by `Decision::parse`) and `ApprovalBroker::answer` for an in-process one that already has the `Decision` (`Once`, `Always`, or `Deny { message }`, whose message is pushed to the run's `Steering` queue so the agent reads it as guidance). An unknown id means the request already timed out, and an unanswered request denies after `APPROVAL_TIMEOUT` (5 minutes) so a turn cannot hang. `list`/`clear` read and edit the project's saved rules.
- `crates/core/src/approvals.rs` — the persisted side of it: per-project `allow` sets in `<config>/Oxide/approvals.json` (`load`/`is_allowed`/`allow`/`list`/`clear`), migrated once from the desktop's legacy `<config>/Oxide/desktop/approvals.json`, so an `Always allow` answer holds across the terminal, the desktop app and the VS Code extension.
- `crates/core/src/ask.rs` — the interactive question side of an agent run, which is what a skill that needs a decision asks through: the agent-level `ask` tool takes 1–4 questions (`question`, an optional `header` used as the dialog's heading, up to 8 `options` of `label`/`description`, and `multiSelect` for a list more than one label may be picked from; a question with no options is answered in the user's own words), `parse_questions` trims, de-dupes and caps them while accepting a single question object, an option written as a plain string, or a `multiSelect` spelled out as `"true"`, and `format_reply` hands the answer back to the model as the tool's result. `AskBroker` mirrors the approval broker — an `Asker` callback that emits `AgentEvent::QuestionRequest { id, questions }` on the run's own stream and awaits the answer for that id — with `AskBroker::resolve` for a front-end that has wire values (an empty answer list is `Reply::Dismissed`) and `AskBroker::answer` for an in-process one. An unanswered request returns `None` after `ASK_TIMEOUT` (5 minutes), which the tool reports as nobody having answered, so a turn cannot hang, and it emits `AgentEvent::QuestionClosed { id }` as it gives up (framed as `question_closed`, `crates/core/src/cli.rs`) so a front-end that painted the questions stops taking an answer nobody will read; a front-end that answered, or a run that ends with a request still open, already knows and is told nothing. The asker is optional on every run (`Runtime.ask` / `AgentRun.ask` are `Option<Asker>`), so `ask` is only offered where a front-end can answer it — the desktop app and an `--mode rpc` client that passed `--ask-questions` — and a TUI or print run never has the model ask a question nobody can see.
- `crates/core/src/compact.rs` — Pi-style context compaction. Walks back from the newest message until `keepRecentTokens` is reached, summarizes the older span with a structured handoff format (including cumulative read/modified file lists; the format request is sent after the wrapped transcript, matching Pi, so the summarizer does not continue the conversation), and never cuts between a tool call and its result. Settings live under `compaction` in `settings.json`/`.oxide/settings.json` (`enabled`, `reserveTokens`, `keepRecentTokens`, per-model `modelOverrides`), with `OXIDE_COMPACTION_*` env overrides. Auto-compaction runs in the agent loop once provider-reported usage crosses `contextWindow - reserveTokens`; it appends a `compaction` entry to the session branch anchored at `firstKeptEntryId`, and the session rebuilds the outgoing view from the leaf path — the anchor is resolved through `context_ids`, which lists only entries that carry a message (a name, model or thinking-level change contributes no message and would otherwise shift the boundary onto a neighboring entry), so a call and its results are never split by a bookkeeping entry. Branch summarization reuses the same structured format: `/tree <n>` branches the current session in place (appending a `branch_summary` entry) and `/fork <n>` creates a new session seeded with the summarized abandoned path. Manual compaction is `/compact [focus]` (TUI) and `oxide sessions compact`.
- `crates/cli/src/tui/markdown.rs` — dependency-free Markdown renderer for assistant messages: parses headings, paragraphs, fenced code, ordered/unordered/nested lists (with `☐`/`☑` task markers), blockquotes, rules, pipe tables, and inline bold/italic/strike/code/links/autolinks into styled `ratatui` lines wrapped to the pane width. `render_with_prefix` merges the `◆ oxide` speaker label onto the first line by wrapping the body with that line's width reserved (`Renderer::first_width`, which every block honours, taking off the indent a list marker, quote bar or ambient already carries), because wrapping the body first and re-wrapping only its first line breaks the paragraph twice and orphans its tail; unclosed delimiters stay literal so a reply renders cleanly while it streams.
- `crates/core/src/diff.rs` — dependency-free line diff for the TUI: `preview(old, new)` returns `None` when unchanged, a one-line summary when either side exceeds `MAX_DIFF_LINES`, otherwise an LCS-based unified-style preview that keeps `CONTEXT` lines around each change and inserts `⋯` gap markers between disjoint hunks. `lines(old, new)` is the same alignment as the lines themselves — each carrying its `LineKind` and the number it holds on each side, and none on the side it is missing from, with `Diff::Same`/`Diff::Omitted` for the two cases a preview renders as a summary — which is what a front-end painting both sides of a change reads.
- `crates/core/src/html.rs` — dependency-free HTML to Markdown/plain-text conversion for `webfetch`: a small tag parser, entity decoding, and a renderer for headings, paragraphs, lists, tables, links, images, code, and blockquotes.
- `crates/core/src/lsp.rs` — minimal LSP client (rust-analyzer, typescript-language-server, pyright, gopls) that reports diagnostics; a `diagnostics` tool is exposed and `write`/`edit` append diagnostics for the edited file. A cached server that exits or whose pipe breaks is evicted from the manager (killing the child) and a fresh one is connected before the call is retried, so a one-off crash does not turn every later edit into `Broken pipe`; EOF while awaiting diagnostics is treated as a disconnect rather than a clean result. A server that still cannot be talked to after the fresh attempt is treated as absent — remembered so it is not respawned, and reported as no diagnostics — so a broken toolchain (a `rust-analyzer` shim missing from the active toolchain, say) does not append `lsp server closed the connection` to every edit.

- `crates/core/src/tools.rs` — tool specs and execution under Pi-style names (`read`, `write`, `edit`, `bash`, `grep`, `find`, `ls`, `webfetch`) plus connected MCP tools; legacy aliases (`read_file`, `write_file`, `patch`, `list_dir`, `glob`) are accepted via `canonical_tool_name`, which every name comparison routes through. `execute(call, cwd, &McpRegistry, &Progress)` returns a `ToolOutput` (text plus optional image/PDF media parts, an optional `DiffPreview` for `write`/`edit`, and a `terminate` flag; `read` attaches images/PDFs); `bash` streams stdout/stderr through `Progress`. Output is capped centrally in `execute` by lines (`MAX_OUTPUT_LINES`) and bytes (`MAX_OUTPUT_BYTES`): `bash` keeps its tail so the exit code survives, other tools keep the head, and dropped content is written under `truncated/` in the Oxide config dir (`OXIDE_TRUNCATION_DIR`, retained 7 days) with a pointer in the result. `read` splits lines longer than `MAX_LINE_LEN` into continuation chunks and pages via `offset`/`limit`, so a minified JSON line can be read through instead of being cut off, and its output budget reserves a line for the `… more lines; use offset=` pointer so the continuation hint is never trimmed. Argument shapes models get wrong are tolerated: `offset`/`limit` accept a numeric string or a range array (`[820, 850]`, which sets the span), and `edit` repairs a stringified `edits` array that was closed with one brace too many (`[{"oldText":…}}]`). A non-exact `oldText` still lands when only trailing whitespace differs or it was copied from `read` without stripping its `N|`/`N+|` numbering; every edit in a call is matched against the original file (so an earlier edit cannot invalidate a later one) and overlapping ranges are rejected instead of guessed, while a genuinely stale one fails with the closest region (its line range and raw text) to copy or, for a block that matches nowhere, a note that each call edits one file. A `bash` command that hits its timeout returns the output it produced before being killed instead of discarding it, plus a hint that steers the retry to a narrower command (a directory scope, a build-output exclusion, or the `grep`/`find` tools) instead of letting the same one time out again. A failed command whose output shows an unresolved relative import (`Cannot find module './...'`) gets a hint: when the Node require stack names a script outside the working directory the hint steers to a script inside the project or an absolute path, and otherwise it steers to checking the specifier, since Node resolves `require('./...')` against the script's own directory, not the working directory. `read`/`ls`/`find`/`grep` accept absolute paths; `ls` renders symlink targets as `name -> target`; `grep` matches a literal substring by default (set `regex: true` for a regular expression) and prefers `ripgrep` when it is on `PATH`, falling back to a parallel built-in walker that sniffs and skips binary files. A search that found nothing answers in Pi's own words rather than with an empty string, which reads as a failure and invites a retry — `NO_MATCHES` (`No matches found`) for `grep`, `NO_FILES_FOUND` (`No files found matching pattern`) for `find` — while an `edit` keeps Pi's `Successfully replaced N block(s) in {path}.`: the redundancy a reader sees is the renderer's to drop, not the result's, which is why Pi's `renderers/edit.ts::formatEditResult` returns nothing on success and the TUI paints `Edited <path>` plus the diff with no restatement line.

- `crates/core/src/updates.rs` — the release trains, resolved once for every front-end: `Component` (`Cli`/`Desktop`/`Extension`, each with its tag prefix and the label a dialog names it by), the `Release`/`Artifact`/`Check` shapes a front-end reads, and `latest()`/`manifest_release()`/`api_release()` — the newest release of a component, preferring the `Oxide-manifest` the installers read and falling back to the API's release list filtered to that component's tags, so a `desktop-v*` or `extension-v*` release is never mistaken for a CLI one; `platform()` picks the artifact this machine installs (a `.dmg` for arm64/x64 macOS, the AppImage/deb/rpm for Linux, the NSIS `-setup.exe` for Windows) out of a release, with the digest GitHub reports beside it. `is_newer`/`should_install` are the SemVer comparison (`+…` build metadata carries no precedence, a numeric pre-release identifier comparing as a number, an unparseable version — a source build's `0.0.0` — treated as older so an update is offered), `fetch`/`download` the transfer, `verify_sha256` the checksum, and `WorkDir` the private 0700 scratch a download lands in. `oxide update` (the CLI's own train), `crates/desktop/src/update.rs` (the app's) and the VS Code panel's check all resolve through here, so what a release is and which tag belongs to whom is answered once.
- `crates/core/src/update_notice.rs` — the "update available" notice a launch shows, held once so every front-end reads the same answer: the newest release of a component, remembered in `updates.json` beside `config.json` as a `Notice` (version, tag, the release page, and when it was found) and read back on the next launch whether or not it could be refreshed, because a launch must not wait on the network for it. `refresh` looks the release up through `crate::updates` and remembers it, and an answer older than `REFRESH_AFTER_SECS` (6 hours) is the only one a launch looks up again — long enough that a daily launch costs one request, short enough that a release cut today is offered tomorrow. `Notice::is_update_for` is the shared SemVer comparison (`is_newer`), so a source build's `0.0.0` is offered the release while a newer running version is not. `checkForUpdates` in `settings.json` — the project's `.oxide/settings.json` winning over the global one, `OXIDE_CHECK_FOR_UPDATES` overriding both — decides whether a launch looks at all, on by default, and `enabled`/`save` are that flag read and written (`OXIDE_UPDATES_FILE` redirects the file, which is how a test or a caller with its own config directory points it elsewhere). The terminal is the front-end that shows it (`ChatItem::Update`); the file is per component, so a front-end that offers another train's notice neither waits for nor overwrites this one's answer.
- `crates/cli/src/install.rs` — how the running binary was installed, held once for `oxide update` and `oxide uninstall`: `detect_install_method` recognizes a Homebrew Cellar, Cargo's `~/.cargo/bin`, and the `~/.local/bin` or `%LOCALAPPDATA%\Programs\Oxide` a prebuilt archive is unpacked into — and any other directory marked by the `.oxide-install` file `record` writes beside the binary, which both installers leave and `oxide update` rewrites when it replaces one, so a custom `OXIDE_INSTALL_DIR` is still a released install — and reports `Unknown` for anything else — a `target/debug` build, a distribution package, a binary someone moved — so a command that is about to replace or remove it checks before it does.
- `crates/cli/src/update.rs` — `oxide update`: resolves the newest CLI release from the shared `oxide_core::updates` (`--component cli`, its default) and installs it the way the installers do — verifying the archive against the checksum, unpacking into a private temp directory, running the unpacked binary's `--version` before it replaces a working one, then renaming a copy beside its destination — while the resolution itself (which tag belongs to which component, the platform artifact, SemVer, checksums) lives in `crates/core/src/updates.rs`, so `oxide update --check --json --component desktop|extension --current <v>` answers the same question for a front-end that installs that release itself: the desktop app's **Check for Updates…** (`crates/desktop/src/update.rs`) reads it for a `desktop-v*` bundle and the VS Code panel (`editors/vscode/src/core/updates.ts`) for an `extension-v*` `.vsix`. `--version` takes a tag or a bare version, `--check` reports and stops, and `-f/--force` reinstalls — see the module docs for the details of each.
- `crates/desktop/src/update.rs` — the desktop app's own release train: `installation()`/`installation_of()` read what this copy is (a macOS `Oxide.app` bundle, the AppImage it runs from, a Windows installer's directory, a distribution package or a checkout's build) and whether it may be written over from inside the app — probed by writing a file beside it, since a mode bit says nothing about who is running — `resolve()`/`check()` resolve the newest `desktop-v*` release through `oxide_core::updates` and report the artifact this platform installs (`Check`), and `install()` re-resolves at the click, verifies the download against the release's digest and puts it in place the way this copy was installed (a `.dmg` mounted read-only with its `.app` staged beside the installed bundle before being renamed over it, an AppImage written beside its own file and renamed, a Windows NSIS installer launched), reporting the path it landed at. ## Conventions

- Rust 2021 edition, 4-space indent, default rustfmt style.
- Errors use `anyhow::Result` with `.context(...)` / `.with_context(...)` for human-readable messages.
- Do not add comments unless they explain non-obvious intent.
- Keep changes small and focused; verify with `cargo test` and `cargo clippy`.
- Built-in file/shell tools and connected MCP tools are registered in `tools::specs(&McpRegistry)` and dispatched in `tools::execute(call, cwd, &McpRegistry, &Progress)`. Tool names are canonicalized with `tools::canonical_tool_name`, which accepts Pi names (`read`, `write`, `edit`, `ls`, `find`) and legacy names (`read_file`, `write_file`, `patch`, `list_dir`, `glob`); permission rules, concurrency checks, and TUI rendering must go through it. `edit` is targeted text replacement (`edits[].oldText` must match uniquely against the original file) and stays separate from the unified-diff `patch` tool. Matching is byte-exact first, then a line-wise pass that ignores trailing whitespace, and a block copied from a numbered `read` listing has its `N|`/`N+|` prefixes stripped (from the replacement text too); leading indentation is never ignored, so a replacement cannot silently lose its indentation. A non-unique match is still rejected, naming the occurrence line numbers, an absent one names the closest region (its line range and raw text, so copying it back applies exactly), and every failing edit in a batch is reported together while nothing is written. `find`/`grep` honor `.gitignore`; `grep` prefers `ripgrep` when available and otherwise uses a parallel built-in walker. The agent-level `task`, `skill`, `command`, `memory`, `diagnostics`, and `ask` tools are defined and dispatched in `crates/core/src/agent.rs`.
