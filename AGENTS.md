# oxide

An optimized AI coding agent CLI written in Rust.

## Layout

The repository is a Cargo workspace. Shared agent code lives in
`crates/core/`; the terminal binary in `crates/cli/` (`main.rs`, `tui/`,
`theme.rs`, `uninstall.rs`); the Electron desktop app in `crates/desktop/`
(`electron/` is the window — the main process, the preload and the packaging —
and `src/` the Rust harness it starts: `manager.rs`/`turn.rs`, the window's own
command layer, and a single `oxide_invoke` command the page reaches through the
preload's bridge, one JSON packet per line between the two halves). The Cargo
package names are `oxide-core`, `oxide` (the CLI), and `oxide-desktop`. The VS
Code extension in `editors/vscode/` is a separate pnpm/TypeScript package, not a
Cargo workspace member: it drives the installed `oxide` binary as
`oxide --mode rpc`, with the prompt and any tool approval travelling on the
child's stdin, so it shares the same on-disk configuration and session
tree without linking `oxide-core`. The CLI and desktop link `oxide_core`
directly (`config`, `session`, `runner` for starting a turn, `updates` for the
release a front-end installs, and `theme_view` for themes as CSS-ready colors).
The desktop resolves project trust from the same `trust.json` the CLI uses and
asks **Trust this project?** before loading a project's `.oxide` agents,
commands, skills and plugins, so its harness matches the CLI instead of being
silently dropped. It accepts image, PDF and text attachments the way the CLI does — paste
from the clipboard or pick files — by passing them to `runner` as inline content
parts (the webview has no on-disk path for a pasted image), and previews each one
as a clickable thumbnail; the webview refuses a file over the core's 20 MB
attachment limit before it is read into a data
URL — the only door it closes, since a format no provider takes and the
machine's image tools can convert (a TIFF, a HEIC) is converted by the core, and
anything else that is not media travels as the text the core attaches it as —
and `commands::attachment_parts` reports a refusal from the core instead of
dropping the attachment from the message silently; it also resolves the message's
own `@path` image/PDF references through `oxide_core::media::referenced_attachments`,
so a reference typed in the composer attaches the same files the terminal's does.
The composer completes an `@path` reference the way the terminal's does, because
both ask the same rules: a keystroke that leaves an `@` under the caret asks the
host (`commands::at_suggestions`), `crates/desktop/src/at.rs` turns the webview's
UTF-16 caret into bytes and answers from `oxide_core::at` over a walk of the
project it keeps until the project changes, and the rows are drawn in the command
palette's own box above the composer (`#at-list` in `ui/index.html`) — `↑`/`↓`
walk them, `Enter`/`Tab` takes one, `Escape` closes the list, a folder keeps the
reference open and a file closes it with a space, and an answer for a value the
reader has typed past is dropped rather than painted under a caret it no longer
belongs to; `ui/check-app.mjs` drives every one of those through a stubbed
bridge, and, over the same stub, that the `/` palette lists a skill under its own
name — the row carrying the name, its arguments and the `skill` badge, taking it
completing the composer rather than running it, and the line it completes to
reaching the agent as the prompt the CLI expands, which is what loads the skill. - `crates/core/src/mcp_config.rs` — `oxide mcp add/list/get/add-json/remove/auth/disable/enable`: reads and writes MCP servers in the native `.oxide/mcp.json` files (`--scope project|global`), merging sources for listing in the same precedence the runtime loads (Claude Code global, `~/.oxide`, the platform config dir, then the project), with a global file reported once as global when the project root resolves to the home directory; `auth`, `remove`, `disable` and `enable` keep a pinned `--scope` inside that scope's files in both layouts (`--scope project` covers a Claude Code `.mcp.json` as well as `.oxide/mcp.json`, so a name defined in both scopes resolves to the requested one), while an unpinned command searches every source in precedence order. `disable`/`enable` write both spellings — `enabled`, and Claude Code's `disabled` kept in step (written when turning a server off, dropped when turning it on) — so the file says the same thing to a harness that reads either one, and a server can be turned off without losing its configuration; a name whose entry is not an object, or that is nowhere while a source cannot be parsed, is reported instead of being passed over or written elsewhere. `mcp list --json` prints a `ServerView` per server — name, transport, detail (URL or command line), the `source` file's label, the `scope` (`project`/`global`) a toggle should pin to, `enabled`, the machine-readable `state` from `McpStatus::state()` (`connected`/`needs-auth`/`needs-trust`/`disabled`/`error`) and its display `status` — which is what the desktop dialog and the extension's `/mcps` dialog draw; `server_views(cwd)` is the same listing for an in-process caller, and `set_enabled` the same toggle. - `crates/core/src/commands.rs` — the shared slash-command catalog: the built-in client commands with their descriptions, fixed argument grammars and a `Kind` (`client` for a command a front-end performs itself, `prompt` for one it runs by sending `/name args`, `skill` for a configured skill, which is listed under its own name — sending `/name` loads it, and `/skill:<name>` is the terminal's other spelling of it), plus the commands, prompt templates and skills the project (and its plugins) contribute, discovered through `crate::ecosystem`. An agent contributes no entry — it is not a slash command but a subagent a front-end selects with its own picker (`/agent` in the terminal, `--agent` for a run), and a command whose frontmatter declares `agent`/`subtask` routing is an ordinary `prompt` entry the CLI routes when it runs it, so a client only sends the prompt. `palette(root)` is what the desktop's `/` palette draws, `builtin(name)` resolves a name, and `list(root, json)` backs `oxide commands`. `FrontEnd` (`Terminal`/`Desktop`/`Panel`) is the membership every built-in declares in its `front_ends`, with `offered_to`/`builtin_entries_for(front_end)` the menu one of them draws, so a name is declared here once and each front-end lists the commands it performs rather than the ones it cannot answer — `/agent` is the panel's, `/permissions` and `/theme` the terminal's and the desktop app's, and `/permissions`, `/theme` and `/logout` are left out of the panel's palette by that field alone. `desktop_only` is still printed for a client too old to read `front_ends` — derived from it, not a second decision. The catalog holds exactly one spelling per command, so `canonical_slash` only normalizes a typed `/name` (trimmed, lowercased, canonical case back) and every front-end keys off that one spelling: a word the catalog does not declare — `/mcps`, `/approvals`, `/cost`, `/thinking`, `/access`, `/login` — is a message rather than a second name for a command, since the alternative was a name that reaches the model as the literal text it was typed as. No front-end keeps a hand-written table of names: the desktop's `slashName` normalizes and the catalog decides, and the panel reads `front_ends`.
- `crates/core/src/config.rs` — `Config` struct; loads `config.json` from the Oxide config dir (`dirs::config_dir()/Oxide`, e.g. `~/.config/Oxide` on Linux, `~/Library/Application Support/Oxide` on macOS) plus `OXIDE_*` / provider env overrides. The `PROVIDERS` table of `ProviderPreset` is the single place a provider is declared — its name, label, description, key URL, aliases, `ProviderKind` (the wire dialect: `OpenAi`, `Anthropic`, `Gemini`, `Bedrock`), `AuthStyle` (`Bearer`, `XApiKey`, `Portkey`, `Google`, `Azure`, `Vertex`, `Aws`, `Copilot`, `Gitlab`), base URL and its env override, default model, key variable(s), `local` flag and any bundled catalog — and every consumer reads it: `auth::known_providers()` builds the login picker from it, `canonical_provider` resolves a name or alias to it, `key_envs` is what the credential is looked up under, `provider_kind` selects the client, and `auth_style` selects the URL shape and the header. Adding an OpenAI-compatible provider is one entry; a provider that speaks another API adds a `ProviderKind` variant, the client that serves it, and the `endpoint_url`/`auth_style` handling beside the existing ones. `for_name` resolves a name, `for_base_url` resolves a host (so a custom provider pointed at a known host is read for its dialect), and `endpoint_url` builds what is per-provider: `{base}/chat/completions` and `{base}/models` for OpenAI-compatible hosts, `{base}/messages` for Anthropic, the Gemini `generateContent` path (with project/location for Vertex), the Bedrock endpoint (empty; the client signs its own), and Azure's `{host}/openai/deployments/{deployment}/chat/completions?api-version=` — whose endpoint comes from `AZURE_OPENAI_ENDPOINT`/`AZURE_OPENAI_RESOURCE`/`AZURE_RESOURCE_NAME` and whose version is `AZURE_OPENAI_API_VERSION`/`AZURE_API_VERSION` else the `AZURE_API_VERSION` default (`2024-10-21`). Portkey keeps custom gateways/config IDs and model catalogs (`PORTKEY_MODELS`), and its Config ID is written to `portkey_config` beside the active selection rather than to a map keyed by provider, since it is Portkey's own setting — a login that chose one is still routed by it on the next launch, whatever provider that launch is on; a provider whose catalog cannot be listed carries its models in the entry, and `merge_model_catalog` leaves a known provider's live listing alone. A provider is local by the table rather than by its URL, so `require_api_key` returns an empty key for one; the same check (`require_api_key_with`, its environment injected so the rule is testable) accepts an empty key for the two providers whose credential this config does not hold — Bedrock, whose SigV4 credentials come from the environment or `~/.aws/credentials`, and Vertex, whose token is minted from a service-account file (`GOOGLE_VERTEX_CREDENTIALS` holding the JSON, `GOOGLE_APPLICATION_CREDENTIALS` its path, or the file `gcloud auth application-default login` writes) — each of them reporting what to set when there is nothing, and the refusal naming every env var a preset accepts rather than only the first. Defines the `Reasoning` enum (`auto` / `off` / `minimal` / `low` / `medium` / `high` / `xhigh` / `max`, set via `--reasoning`, `OXIDE_REASONING`, or config) plus `ModelReasoning`, the per-model `effort.supported_levels`/`default_level` a provider listing advertises (DeepSeek carries them): `Config::load` reads the model cache into `reasoning_supported`, `reasoning_levels()` offers the model's own set (with `off`), `effective_reasoning()` clamps a choice onto it (walking up first, Pi's rule), and the TUI/desktop pickers cycle those levels rather than a fixed list, composes the system prompt (a `# Definition of Done` section that forbids reporting unobserved work and requires confirming the outcome of any state-changing action — edits/builds, pull requests, comments and reviews, releases, deployments — before claiming success, while letting an explicit instruction from the user outrank every one of those checks — a "no need to check the PR's status" is followed and the reply says plainly what was left unverified rather than the check being run anyway and holds a review fix until it is committed and pushed before the reply in the thread, a `# Scope` section that keeps commits and PRs limited to the paths the task touched and forbids blanket staging, tool-use guidance that steers toward the dedicated `read`/`grep`/`find`/`ls` tools over compound shell commands (including codebase searches, which a repo-root shell `grep -r` runs through build output and `.git/` while the tools skip both and honor `.gitignore`), and the loaded ecosystem — listing skills, commands and subagents for model auto-invocation, plus a `# Plugins` section naming every plugin the run knows about with the description and the capabilities it brought (`2 skills, 1 command, 1 MCP server`), one marked `(disabled)` when it is installed but switched off, and how many hook plugins are active, so a request that belongs to a plugin is met with what it provides instead of the model building a workaround or telling the user to install a plugin that is already there), resolves `/commands` (including `agent`/`subtask` routing and a skill by its own `/name`, with `/skill:<name>` kept as the terminal's alias), and loads context-compaction config from `settings.json` and `.oxide/settings.json`, plus `steeringMode`/`followUpMode` (project wins per key, unknown values keeping `one-at-a-time`) into `steering_mode`/`follow_up_mode` for the run's queue delivery. `context_window()` resolves the model window the way Pi's catalog does — `OXIDE_CONTEXT_LIMIT`, then an explicit `context_window` field, then a `modelContextWindows` override from the global/project `settings.json`, then the window the provider's own catalog published (`crate::catalog`, remembered beside `config.json`, a provider offering less than the model's default included: Bedrock's Claude Sonnet 4.5 is 200k where Anthropic's is 1M), then a built-in table of models.dev windows (a routed or Bedrock-spelled id matching by its basename, so `anthropic/claude-opus-4.7` and `us.anthropic.claude-sonnet-4-5-…` resolve the same), then Pi's `128000` fallback — and keeps it at least as large as `max_tokens`. Switching providers remembers the model and custom endpoint last used with each one (`provider_models` and `provider_base_urls` in `config.json`, with the active provider's endpoint mirrored to `base_url`) so each login keeps its own model and gateway, and `for_provider` builds a copy of the config pointed at another logged-in provider for catalog queries. `Config::load` also reads the local projects (`crate::workspaces`) into the `# Workspaces` section, so the composed prompt names this run's directory and the other folders added to Oxide, and the `# Tool use` guidance forbids a `find ~` sweep as well as `find /`.
- `crates/core/src/catalog.rs` — the model catalog pi.dev publishes per provider, which is where the context window of a model the built-in table does not know comes from: `GET {base}/api/models/providers/{id}` (`BASE_URL` = `https://pi.dev`, `OXIDE_MODEL_CATALOG_URL` a mirror of it), revalidated with the ETag it returns and remembered in `model-catalog.json` beside `config.json` as a `CatalogEntry` per provider (`checked_at`, `etag`, `models`), so a launch reads the windows off disk and never waits on the network for them — a `304` and a transient failure both keep the models and the validator a lookup could not improve on (only the freshness moves, so a broken lookup is not retried at every launch), a `404` remembers that the provider is answered for no longer, and the store is replaced through a temporary name so a reader never sees half of it. `REFRESH_AFTER_SECS` (Pi's own four hours) is when a launch looks again: `refresh_if_stale` looks one provider up only when its remembered entry has reached that age, and `refresh_launch` — the one call the terminal (`crates/cli/src/tui/mod.rs::spawn_model_catalog`) and the desktop harness (`crates/desktop/src/commands.rs::auto_catalog`) both make — runs it over `launch_providers(active)`, every provider the machine holds a credential for plus the one `config.json` selects (Bedrock and Vertex hold no key here and are the ones a catalog answers for most usefully, since `auth::stored_providers` cannot name a credential the machine already holds), handing back the windows only when one of those lookups changed them, since what was already there reached the run through `Config::load`; `window_for(models, model)` resolves an id the way the table does — the exact id, then both sides stripped of their vendor and region prefixes (`us.anthropic.claude-sonnet-4-5-…` is `claude-sonnet-4-5-…` to the catalog), then the table's own longest-prefix rule — and `provider_id(provider)` is the pi.dev id an Oxide provider is asked under (`moonshot` → `moonshotai`, `bedrock` → `amazon-bedrock`, `vertex` → `google-vertex`, `vercel` → `vercel-ai-gateway`), `None` for a provider pi.dev publishes no catalog for (Portkey and a local runtime, whose models are another provider's, and the hosts it does not answer for). `Config::catalog_windows`/`catalog_window()` read it in `context_window()`, between the `modelContextWindows` override and the built-in table, so a provider's own published window — a provider offering less than the model's default included, as Bedrock does with Claude Sonnet 4.5's 200k against Anthropic's 1M — is the one a run resolves; `modelCatalog` in a `settings.json` (the project's `.oxide/settings.json` winning per key, `OXIDE_MODEL_CATALOG` overriding both) turns the lookups off for a machine with no network, while the remembered windows are still read, since reading them touches no network, and `OXIDE_MODEL_CATALOG_FILE` redirects the file so a test or a caller with its own config directory points it elsewhere.
- `crates/core/src/auth.rs` — stores provider API keys/tokens for any number of providers side by side in `auth.json` in the Oxide config dir (mode 0600); keys are resolved after env vars and before the config file. Authentication is TUI-only (`/login`, `/logout`), matching Pi: `connect` also writes the active provider to `config.json` so the next launch uses it, `select_stored` adopts a provider that is already saved so switching between logged-in providers never asks for the key again, and `stored_providers` lists them. The provider list the picker and the suggestion list draw comes from `config::PROVIDERS` (`known_providers()`, built once), so a provider is never listed in one place and missing from another, and `canonical_provider` maps aliases onto the canonical names (`gpt`/`gpt-4o` → `openai`, `port-key` → `portkey`, `glm`/`z.ai`/`zhipu`/`bigmodel` → `zai`, `copilot`/`github` → `github-copilot`). `device_flow_client` names the OAuth application of a provider whose login is a browser flow rather than a pasted key (`AuthStyle::Copilot`; `crates/core/src/llm/copilot.rs` owns the flow), so the TUI's connect dialog knows to run it instead of asking for a key. `ProviderView`/`provider_views()` are the one provider listing every picker draws — the name a login takes, the label and description it paints, `keyUrl`, `stored`, `active`, and a `CredentialMode` (`key`, `external`, `none`) saying where the credential comes from, so a provider that signs with a credential the machine already holds (Bedrock's AWS identity, Vertex's application-default file) is not asked for a key nothing would read; `login_provider` is the login behind `oxide login` and the desktop's Connect dialog, and `resolve_login`/`select_stored` accept the external-credential providers with no key. There is no `oxide auth` subcommand.
- `crates/core/src/ecosystem/` — discovers and loads configuration from project and global scope: the native Oxide layout (`.oxide/`, `AGENTS.md`, `.oxide/mcp.json`) plus the Claude Code layout (`.claude/`, `CLAUDE.md`, `.mcp.json`) for compatibility. Context files (`AGENTS.md`/`CLAUDE.md`, with `AGENTS.override.md` replacing its directory) are collected by walking every ancestor directory down to `cwd`, and `.oxide/SYSTEM.md`/`APPEND_SYSTEM.md` replace or extend the system prompt. Covers instructions, commands, prompt templates (`prompts/*.md` with Pi-style argument expansion), agents/subagents, skills (`SKILL.md`), MCP servers and plugins. Installed plugin packages contribute their `commands/`, `agents/`, `skills/`, and MCP servers — read from the manifest `mcpServers` or a plugin-root `.mcp.json` in either the wrapped or bare-map form — and each loaded plugin is recorded as a `PluginSummary` alongside the counts of what it contributed, so the prompt can describe it by what it shipped; a plugin that is installed but disabled is recorded too (without contributing anything), so a request it answers is not met with a workaround or a fresh install. Project-scope resources are gated behind project trust via `ecosystem::load_opts`. This repository keeps its own agents, commands, prompts, skills and plugins in `.oxide/`; user-facing configuration guidance lives in `docs/cli.md` (task guides) and `docs/configuration.md` (reference tables).
- `crates/core/src/trust.rs` — project trust: `TrustStore` persists per-directory decisions in `trust.json` (closest ancestor wins), `requires_trust` detects project-local resources, `resolve` applies the CLI override plus `defaultProjectTrust` (read from `settings.json`), and untrusted projects reload without project resources (context files still load).
- `crates/core/src/workspaces.rs` — the local projects a run is told about: reads the desktop's project registry (`desktop/projects.json`, the folders added in the app), keeps the ones that still exist and are not the run's own directory (the run's directory is resolved to its absolute, filesystem-resolved form first, so a relative `-C .` is recognized as the project the desktop recorded rather than listed beside itself), and orders them with the current project's sibling first and then by most recently opened (capped at `MAX_LISTED`, the rest counted), so `Workspaces::section()` can name this run's directory and every other project Oxide knows with its path in a `# Workspaces` section of the system prompt. That is what answers "can you reach the `<repo>` repo?" and what says the file tools take absolute paths — a file in a sibling project is readable, searchable and editable from the run, while `bash` still starts in the current project's root — so the model resolves a repository from the list rather than a `find ~` that reads every unrelated file on the machine until the command times out. A registry that is missing, unreadable or malformed leaves a run knowing nothing but its own directory, and `Config::load` reads it once per run so the CLI, the desktop app and the VS Code panel are told the same thing.
- `crates/cli/src/theme.rs` — semantic TUI color themes: built-in `dark`/`light` (built from `oxide_core::theme_view` so they match the desktop), custom `.oxide/themes/<name>.json` (color names or `#rrggbb`), selected with `--use-theme` or `/theme`. Slots cover focus, speakers, success, tools, errors, supporting text, borders, tool panel backgrounds (`tool_pending_bg`/`tool_success_bg`/`tool_error_bg`), the Portkey spend bar (`usage_bar_bg`/`usage_bar_fg`/`usage_bar_label`), thinking levels, and `thinking_text` for reasoning blocks.
- `crates/core/src/agent.rs` — agent loop: stream the model, execute requested tools, and feed results back until the model stops calling tools or a batch reports `terminate`. Read-only tool calls in a batch run in parallel (results kept in call order) while mutating tools stay sequential; a `Steering` queue injects user messages typed mid-run before the next model call and a second holds follow-ups for after the run, each holding a `Queued` (the message plus the label a front-end shows it by, since a content part carries the bytes and not the file it came from), delivering one `Queued` per opportunity (`QueueMode::OneAtATime`, Pi's default, or the whole queue when `steeringMode`/`followUpMode` say `all`), and announcing `AgentEvent::Steered` with the message and its label as each is delivered so a front-end paints the turn then rather than when it was queued — a response boundary that injected one sets a flag so the top-of-loop poll does not take the next before the model call it belongs to, and a batch whose results all set `terminate` ends the turn. Hosts the agent-level `task` (subagent), `skill` (on-demand load), `command` (model-invoked commands/prompt templates; `subtask` commands run as subagents), `memory`, `diagnostics`, and `ask` tools; `run` returns a boxed future so subagents can recurse (capped by `MAX_TASK_DEPTH`), and `run_subagent` runs a `subtask` command in an isolated context. A `Runtime` bundles the MCP registry, plugin host, session log, snapshots, LSP manager, the steering and follow-up queues, and the approval callback. Provider-reported token usage (input/output, cache tokens, and cost) is forwarded as `AgentEvent::Usage`, `ThinkingDelta` forwards streamed reasoning and `Retrying` a transient failure about to be retried (the failed attempt's partial text is dropped, and the last attempt's text is recorded to the session when the retry budget is exhausted), `SubagentActivity` carries a nested subagent's tool call up to the originating view (the `task` tool otherwise emits nothing until it returns), and auto-compaction appends a `compaction` entry to the session branch. A `VerificationState` tracks files edited in a run until each is read back, inspected from the shell (a `git diff`/`git show`/`grep` naming the file confirms just that file) or covered by a build/test/lint command, and a table of `DONE_RULES` covers side effects that outlive the workspace (`gh pr create`/`glab mr create`, comments and reviews, releases, deployments and publishes) until a matching status command reads their outcome; if the model tries to finish with any unconfirmed it gets one hidden system reminder (a `# Definition of Done` note) to verify before summarizing (the reminder repeats that a user instruction to skip a check outranks it), and a provider that answers that reminder with no answer ends the run with the summary already in hand instead of surfacing `the model returned an empty response` on top of a complete reply — while a non-empty answer is merged into the summary it re-checked (text and usage together, the step held open so the transcript paints one bubble) so a re-checked run ends with one summary instead of two. A `scope` rule flags blanket staging (`git add -A`/`--all`/`.`/`:/`, `git commit -a`) until a `git status`/`git diff --staged`/`git show` review confirms what is staged. A review reply that ships an edit stays unconfirmed until `git push` delivers it, so a fix left uncommitted while a review is answered is not reported as addressed; a review reply in a comment's own thread (a POST to the `/replies` endpoint) or a top-level comment (`gh pr comment`/`review`, `glab mr note`) is held while the repository has tracked modifications or unpushed commits (which also covers shell edits like `sed -i` or a formatter), so the thread is not answered before the branch has the fix — while an edit outside the repository the run works in (a scratch file, the body of the reply itself, a report under the home directory) is not part of that delivery and holds nothing, since it is not on any branch, and both halves of the guard judge an edit against the same boundary: the repository the run works in, found the way git finds it (the closest enclosing `.git`), so an edit beside a run that started in a subdirectory is the tracked modification `git status` reports rather than a file written outside the project; a single-branch clone's missing remote-tracking ref is resolved by asking the remote for the branch tip with `git ls-remote` (and accepting a tip the local commit is an ancestor of), so a fix that was actually pushed is not held forever. A repeated build/test command in the same run is flagged with a note rather than silently re-run.
- `crates/core/src/llm/` — model client. `client.rs` dispatches on the preset's `ProviderKind`, so a provider's dialect comes from the `PROVIDERS` table rather than from its name: OpenAI-compatible chat completions (most of the table, `AuthStyle::Bearer`/`XApiKey`/`Portkey`/`Azure`/`Copilot` — `authenticate_openai` picks the header, `x-portkey-api-key` for Portkey and `api-key` for Azure, and a Copilot turn re-mints the session token before it builds the request, since that token names the endpoint), the Anthropic Messages API (`anthropic.rs`; `AuthStyle::XApiKey` — Anthropic and MiniMax), Gemini's `generateContent`/`streamGenerateContent` (`gemini.rs`, keyed by an `x-goog-api-key` header for the Gemini API and by an OAuth bearer token for Vertex, whose access token `vertex.rs` mints from a service-account JSON and refreshes as it expires) and the Bedrock Converse API (`bedrock.rs`, whose requests are SigV4-signed by `aws.rs` — `SigningRequest` + `sign` over `ring`/`sha2`, with the credential read from the environment or `~/.aws/credentials`, or a Bedrock API key sent as a bearer token instead of signed — the configured key first, so a stored `/login bedrock` credential is what authorizes the request rather than being passed over), and `fetch_models` follows the same split (a Bedrock control-plane listing, a Copilot session listing, `{base}/models` elsewhere). The Anthropic path (`anthropic.rs`, converting internal messages to content blocks and parsing its SSE events, and marking the system prompt, the last tool, and the newest message with `cache_control: {"type":"ephemeral"}` so each turn reuses the cached prefix instead of re-reading the whole conversation; the OpenAI-compatible path sends the session id as `prompt_cache_key` for direct OpenAI and as `x-session-id`/`x-client-request-id` headers for gateways, so those providers also get cache affinity, and on a Claude model behind a non-OpenAI endpoint it translates the same Anthropic `cache_control` breakpoints into the OpenAI-shaped request so Portkey/OpenRouter can cache the prefix). Applies the configured reasoning level: OpenAI-compatible `reasoning_effort` and Anthropic adaptive or extended thinking, with Anthropic thinking blocks replayed on later turns and every DeepSeek assistant message carrying `reasoning_content` (its thinking mode answers a request that drops an earlier turn's reasoning — tool call or plain answer alike — with a 400, since the request carries tools, and `deepseek-flash` thinks nothing on quick tool calls and short answers, so the field is sent empty rather than omitted; `Config::is_deepseek` matches the provider, the first-party endpoint, and a DeepSeek model behind a gateway); DeepSeek's own API (`is_deepseek_api`) and GLM instead toggle `thinking.type` and map levels onto their `low`/`high`/`max` scale -- `off` disabling it where accepted and asking the lowest effort on forced-thinking models (GLM-5.3 and later, via `glm_forces_thinking`, which reject `disabled`) -- and every provider's request uses `Config::effective_reasoning()`, so a level the model did not advertise is clamped onto the nearest one it did. Streaming goes through `StreamHooks` (`text`, `thinking`, `retry`) so the caller can show work in progress: reasoning deltas (`reasoning_content`/`reasoning`/`reasoning_text`, normalized by `Delta::reasoning`) are merged into one Anthropic-shaped `thinking` block and forwarded as `AgentEvent::ThinkingDelta`; `types::push_thinking` grows that block in place by mutating its `Value::String`, since rebuilding the block per fragment would copy the whole trace and make a long reasoning stream quadratic, and `types::set_thinking_signature` records the signature Anthropic attaches to it. `read_sse` splits the byte stream with `drain_lines`, which hands each complete line to the caller and compacts the buffer once per chunk instead of after every line. A stream that drops without a TLS `close_notify` is remembered as an abrupt end: a turn whose sentinel or stop reason already arrived is returned, but an abrupt close before either is still an incomplete (retryable) turn rather than a partial success, and a plain truncated body is still an error. A retryable failure emits `Retry { attempt, max, delay }` before backing off; a retry may follow an attempt that already streamed text or reasoning, so each front-end drops the assistant or thinking item still in progress when it sees the retry, and the retry streams fresh instead of extending the partial output. `stream_chat` retries transient failures (network errors, truncated streams, 429/5xx) with backoff, retries a turn that carries neither text nor tool calls (`assistant_turn_is_empty`), and only turns empty/truncated streams or in-band `error` payloads into errors once the retry budget is exhausted; an empty or reasoning-truncated turn is reported as the downcastable `NoAnswer` error so a caller that sent a best-effort request can tell it apart from a real failure. A turn whose provider stop reason is the output limit (`finish_reason`/`stop_reason` `length`/`max_tokens`, captured on `AssistantTurn`) instead retries with a doubled `max_tokens` up to 32768, since a reasoning model that spent the whole budget thinking would only truncate again at the same cap. The Anthropic path shares the empty-turn check and treats a `message_delta` stop reason as completion, so a dropped stream is retried instead of returned as an empty turn. Both wire paths repair the outgoing history before serializing it (`repair_tool_pairs`): an assistant tool-call turn stored without its results (a run killed mid-tool, a truncated log) gets a result the provider accepts, and a tool result whose call is gone is dropped, so a 400 (`An assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'`) does not fail every later request against the same broken log.
- `crates/core/src/llm/gitlab.rs` — GitLab Duo: the stored token (a personal access token with the `ai_features` scope, `GITLAB_TOKEN`/`GL_TOKEN`, or one `/connect gitlab` saved) is presented to the instance (`POST {instance}/api/v4/ai/third_party_agents/direct_access`, `GITLAB_INSTANCE_URL`/`GITLAB_URL`, `gitlab.com` else), which answers with a short-lived gateway token and the headers that go with it; that token is what the AI gateway's proxy accepts, and it is cached in memory for `TOKEN_TTL_SECS` (25 of its 30 minutes) so a long session is not re-authorized every turn — a 401 names the scope to grant, a 403 says the account needs Ultimate with Duo, and a 404 says the instance has no third-party agent endpoint. `openai_base`/`anthropic_base` build the two proxies (`{gateway}/ai/v1/proxy/{openai/v1,anthropic/v1}`, `GITLAB_AI_GATEWAY_URL` or the binary's `base_url`, `cloud.gitlab.com` else), and which one a turn takes is the model: `Config::provider_kind` reads a `claude-*` model under this provider as Anthropic's wire and everything else as OpenAI's, so the model is the provider's own name rather than the `duo-chat-*` alias the Duo chat UI lists. `client.rs::gitlab_headers` puts the minted token and its headers on the request beside Anthropic's `anthropic-version` (and no `x-api-key` a direct Anthropic turn would carry), and the same minted token authorizes `fetch_models`, whose listing is read from the proxy the model speaks (`/models` under Anthropic's base for a Claude model) — which is why no `duo-chat-*` catalog is bundled: those are the Duo chat UI's aliases, and the gateway's catalog is the live listing.
- `crates/core/src/llm/copilot.rs` — GitHub Copilot's two-step login: a GitHub token (`GITHUB_TOKEN`/`GH_TOKEN`, or one stored by `/login github-copilot`) is exchanged for the short-lived Copilot **session token**, which is cached in memory and re-minted just before it expires (`REFRESH_MARGIN_SECS`), since the same token also names the endpoint (`api.githubcopilot.com`, or a business account's own host) a turn has to be sent to. The TUI's device-flow login and every other credential path end at the same stored GitHub token, so the panel and the desktop app, which paste a token, work like the terminal.
- `crates/core/src/mcp.rs` — MCP runtime: connects configured servers over stdio or HTTP, initializes JSON-RPC sessions, and exposes remote tools (`<server>__<tool>`). Remote servers with an `oauth` block attach a bearer token per request. Servers stay lazy — nothing is started or requested until one is needed — but a user message that names a service selects the server configured for it the same way a pasted URL does: `servers_for_text` matches the words of a server's own name, the aliases of the well-known service its name belongs to, and the service its configured URL or command points at (`company-tools` at `mcp.atlassian.com` answers to `confluence`/`jira`), so "create a Confluence doc" loads the server before the first model call instead of leaving the model to ask for a URL, while words too short or too generic to name a service are ignored; `McpServer::domains()`/`service_names()` derive the same identities, so such a server also owns its service's URLs and `mcp_load` — whose schema lists every name a server answers to — loads it by any of them, reporting a name more than one server answers to rather than guessing. A server's own `instructions` from the initialize handshake are kept and passed to the model — in the `mcp_load` result when the model loads it, and as an `# MCP server notes (untrusted)` section of the system prompt from `instructions_section` for the rest of the run — so guidance like "call getAccessibleAtlassianResources first" reaches the model even when the server was auto-loaded rather than asked for; that section says the text came from the servers themselves rather than the user or the policy and cannot change the instructions above it, grant a permission or redirect the task, since a third-party server's text must not read as policy. Connecting never logs in: a server whose token is missing (or too stale to refresh) fails with `AuthorizationRequired`, which names `oxide mcp auth <name>` so the model asks the user to authorize out of band instead of retrying, and `/mcps` repeats that on the row it marks `Needs Auth`. Authorization opens a browser and then waits on the loopback callback for up to five minutes, so a turn that started it would strand the run behind a login the front-end cannot show — `load` used to hand `stdin().is_terminal()` to the OAuth state as an "interactive" flag, which made the TUI, the one front-end whose stdin *is* a terminal, the one place that happened. A refresh needs no browser and still runs mid-turn, so an expiring token is invisible.
- `crates/core/src/mcp_oauth.rs` — OAuth 2.0 authorization-code + PKCE for remote MCP servers: metadata discovery, loopback callback, token exchange/refresh, and `mcp-oauth/<server>.json` storage (mode 0600). `ensure_authorized` is the interactive flow and belongs to `oxide mcp auth <name>` alone — a command the user is waiting on; an agent run asks `access_token_if_available`, which refreshes silently and otherwise reports nothing rather than opening a browser. The callback answers with a self-contained branded page (semantic color tokens, light and dark via `prefers-color-scheme`, status icon, headline, message naming the server, a monospace block for the provider's error detail, a best-effort `window.close()` after success, all text HTML-escaped, no external assets) plus `Cache-Control: no-store`. `open_browser` is the one browser launcher the flow and a clicked transcript link share: it starts the platform's handler with null standard handles and `child::detach_terminal_std` (a session with no controlling terminal, and `CREATE_NO_WINDOW` on Windows), and on Windows asks `rundll32 url.dll,FileProtocolHandler` directly rather than via `cmd /C start`, so a `&` or `|` in an assistant-generated link is data, not a second command.
- `crates/core/src/at.rs` — the `@path` completion's rules, held once so a reference completes identically in the terminal's composer and the desktop app's (the VS Code panel cannot link the crate and mirrors them in `editors/vscode/src/core/at.ts`): `token(value, caret)` reads the reference the caret sits in — a word-boundary `@` running to the next whitespace, so an address names no file, and the whole token even when the caret is inside it — and `suggestions(paths, token, max)` ranks the workspace listing its caller supplies (`tools::workspace_paths`, gitignore-aware, files and their parent folders) into rows, case-insensitively: a name that starts with the query, then the whole path that does, then one that mentions it anywhere, capped at `MAX_AT_SUGGESTIONS` (200). A folder's row inserts `@dir/` and keeps the reference open, a file's inserts `@file ` and closes it, and a folder the reference already spells exactly is left out, so taking a row walks *into* that folder instead of completing it to what is already typed.
- `crates/core/src/media.rs` — multimodal attachments, read the way Pi reads them: dependency-free base64 (`base64_encode`/`base64_decode`), `@path` reference extraction, and a best-effort OS clipboard grab. `load_attachment` refuses nothing for its type — a file past `MAX_ATTACHMENT_BYTES` is refused before it is read, an image becomes an image part (one no provider takes as it stands — a BMP, a TIFF, a HEIC, a HEIF, an AVIF — is converted to PNG by `convert_image_to_png` through the tools the platform itself ships: `sips` on macOS, ImageMagick/ffmpeg on Linux, and the imaging stack Windows carries (`System.Drawing`, asked through PowerShell without a console window) — while an image none of them can decode travels as it stands rather than being refused, so a build with no decoder for it loses nothing), a PDF becomes a document part (`is_pdf_path` reads the `%PDF-` header, so a document's bytes decide it the way they decide everything else), and anything else becomes its own text wrapped the way Pi wraps it (`<file name="…">…</file>`, `file_text`), so a `.csv`, a `.json` or a source file needs no format list to travel — a payload whose head holds a NUL byte is refused instead, since it is neither media nor text. `image_mime_of`/`image_mime_of_bytes` let a file's bytes decide (`sniff_image_mime` over `SNIFF_BYTES`, Pi's own sniff window) — a text file called `.png` is not an image and a screenshot saved without a name for it still is — and both routes to a part meet in `part_from_bytes`, so the file a path names and the payload a data URL carries are read by the same rules, while `part_kind`/`attachment_label` name a part for a tool result and the `/attach` listing. `clipboard` answers a `Clipboard` — the part to attach, or what a paste found instead: the types a pasteboard holds when there is nothing on it to attach, the reason a file the copy names cannot be attached, or a pasteboard that could not be read at all — which is the read `clipboard_media` hands the desktop app and the VS Code panel; `clipboard_paste` is the terminal's own read, and answers the `Paste` Pi's `Ctrl+V` inserts: `Paths` for every file a copy names (via `clipboard_paths`, all of them, not just the first) or the scratch file a clipboard image was written to, the clipboard text (`clipboard_text`), or nothing with the types it holds. A picture the pasteboard holds with no file name of its own is written under the config dir (`clipboard/<id>.png`, pruned after 7 days on the next write) and answered with that path, so a paste the copy named nothing for is named like any other attachment — by the id `/attach` lists it by — instead of by its kind, and where that scratch cannot be written the bytes are answered with no path and the front-end falls back to naming the part by what it is. It prefers a file the clipboard holds over its picture — a Finder copy puts the file URL *and* the file's icon on the pasteboard, so the image grab attached a copied screenshot as a `PNG`-document icon; this is macOS-specific, as a Linux or Windows file copy carries no picture to mistake for the file — and a file that is here but cannot be attached is refused with that reason instead of replaced by that icon, while a path this machine does not have (a screenshot or a file copy that arrived from another one, whose URL travelled with the pasteboard but whose file did not) is left to the pasteboard's own image rather than reported as nothing to attach. A read the platform refused for permission is the one refusal the pasteboard's picture can answer — `read_refused` distinguishes it from a folder or a file the size or binary check turned away — so macOS's per-app grant over Desktop, Documents and Downloads leaves the pasteboard's own picture attached (what Pi reads) rather than the grant hint alone, a picture that is the file's icon where the copy was a Finder file, so the hint still names the way to the file itself. The macOS file URL is read out of `NSPasteboard` (AppKit's `readObjectsForClasses:{NSURL}` with `isFileURL`), not by coercing the clipboard with AppleScript's `«class furl»`, which turns any text into a path (`/plain text`, `/https/::host/photo.png`) and only inspects the first pasteboard item — so an icon listed ahead of the file URL failed the coercion and fell through to the icon; reading the real URLs finds the file wherever it sits and answers nothing when there is none. The alias record a Finder-style copy writes is read by a second, plain script, which must not load AppKit: `use framework "AppKit"` points `the clipboard` at the Cocoa pasteboard, whose coercions know only the modern file URL types, so `the clipboard as alias` stops resolving that very record — the one a copy that names no file URL leaves — and the file went unread, leaving the paste with whatever picture the pasteboard carried or, when it carried none, with nothing at all; that script is asked after the AppKit read rather than before it, since a copy carrying a picture is already answered there, and it answers with the path it coerced or with the types the pasteboard holds. The image itself is read the same way (`dataForType:` for `public.png`, then the `public.tiff` a copy from Preview or Safari leaves, converted with `sips`), which asks the item for the type it advertises instead of coercing it — what `pngpaste` does, and the read that fetches a pasteboard whose bytes are not on this machine yet — and it is asked before `pngpaste` (`-`, when it is installed) and the coercing AppleScript, which are then answers for a machine where that read found nothing (`wl-paste`/`xclip` on Linux). `optimize_image` downscales an oversized PNG/JPEG/WebP (long edge 1568, dimensions parsed from the header) with `sips` on macOS or ImageMagick/ffmpeg on Linux in a private randomly named temp directory that is removed on drop, falling back to the original, so a pasted screenshot is not base64-encoded and stored at full resolution — Windows is the one platform with no tool for the resize, since the imaging stack it carries is asked to convert rather than to scale, so an oversized image there travels with the dimensions the front-end sent, which its page and the panel have already bounded on a canvas; `content_part_from_data_url` decodes a desktop data URL before anything else is decided about it and hands the bytes to the same `part_from_bytes`, so a payload declared `image/png` that holds text travels as that text, a PDF declared as one is still read by its header, and a payload past the limit or not base64 is refused before it becomes a part — a data URL never touches a path and is otherwise the one attachment that could stay at full resolution. `MAX_ATTACHMENT_BYTES` (20 MB) bounds an attachment on both routes — `load_attachment` checks the file's length before reading it and `content_part_from_data_url` checks the data URL's decoded size before keeping it — `MAX_DATA_URL_CHARS` is the base64 length of a full-size payload, so a URL at the limit decodes to fewer bytes than `MAX_ATTACHMENT_BYTES` and an image is measured again after decoding — because the bytes exist several times over at once (the front-end's copy, the IPC message, the session entry, the request body), and `is_supported_image_mime` is the set a provider takes as it stands — Pi's own normalized set, PNG/JPEG/GIF/WebP, so a BMP is converted too and a GIF keeps its animation — while each front-end paints only the subset a browser can draw (`isPaintableImage`, which keeps BMP, in the desktop page and the panel), so an image the core converted is sent as a PNG — a TIFF showing a file glyph rather than a thumbnail a browser cannot render, a BMP showing its own picture on the chip. Both return `None`/an error for a refused attachment rather than dropping it silently. `references_attachment` decides a reference in a message: the bytes decide every file this process can open, and one whose head cannot be read at all is taken by its name (`name_claims_media`, the sniff's own set plus the other spelling of each), so a reference to media the app may not read is reported by whoever attaches it instead of reaching the model as the literal `@path` it was typed as. Every read of a file that is about to be attached or inlined goes through `read_error` — `load_attachment`'s own reads, the `@file` an argument names, and the `read` tool's — which names the grant to give the app rather than leaving the reader with an errno: macOS keeps the Desktop, Documents and Downloads folders behind a per-app grant, so the read answers `Operation not permitted` for a file the user can plainly see — and the grant is not this binary's, since TCC answers an access as the *responsible* app, the one the run was started from, so the reason names that app (`responsible_app` walks the process table to the nearest ancestor inside an `.app` and names the outermost bundle on its path by what that bundle says it is — its `CFBundleDisplayName`, else its `CFBundleName`, else the directory it sits in, which is the name the platform resolves that grant under — so VS Code's own helper answers `Code` rather than the `Visual Studio Code` of the folder it lives in, and the desktop app's harness answers `Oxide` — and a run with no app above it, over `ssh` or detached, keeps the words that name no app) instead of sending the reader to a Files and Folders list that holds no such entry.
- `crates/core/src/clipboard.rs` — system clipboard writes for the TUI: always emits an OSC 52 sequence (wrapped in a DCS passthrough under tmux/screen, so copies survive SSH) and additionally tries a native helper (`pbcopy`/`osascript`, `wl-copy`/`xclip`/`xsel`). A copy reports itself with a dim `ChatItem::Status` tip, since `App.status` only renders while the agent is busy.
- `crates/core/src/memory.rs` — persistent cross-session memory store (project + user scope) under `memory/` in the Oxide config dir, with dependency-free tf-idf search.
- `crates/core/src/notice.rs` — out-of-band notices from the core to whatever front-end is running: the things that belong to no tool call and no `AgentEvent` — an MCP server's OAuth flow naming the URL it opened, a plugin runtime that would not start or a plugin package that was skipped, an approval rule that could not be saved. A front-end installs a `NoticeSink` once (`set_sink`, first caller wins, since the first one to claim the screen owns it) and `info`/`warn` route a `Notice` (its `Level` and text) to it; with no sink installed — a `-p`/`--mode json`/`--mode rpc` run, whose stdout is reserved for frames — the text falls back to stderr. That is what keeps these messages off the TUI's alternate screen: ratatui only rewrites cells whose style changed, so a raw `eprintln!` from the core landed as garbled text no later frame repainted, which is why nothing in `crates/core` prints to stderr directly anymore. The TUI takes the sink's notices on a channel of its own in `event_loop` and pushes each one as a `ChatItem::Info` (or `ChatItem::Error` for a `Warn`) with `auto_scroll`, so an authorization URL is a transcript line the reader can scroll back to.
- `crates/core/src/notify.rs` — best-effort desktop toast for a completed agent turn: `send` runs the platform notifier on a detached thread (Notification Center via `osascript` on macOS, `notify-send` plus the freedesktop `complete` sound via `canberra-gtk-play`/`paplay`/`aplay`/`ffplay` on Linux, a WinRT toast with `Notification.Default` audio on Windows). `load_config` resolves `notifyOnComplete` and `notifySound` from the global and project `settings.json` (project wins per key) with `OXIDE_NOTIFY_ON_COMPLETE`/`OXIDE_NOTIFY_SOUND` overrides; both default on; the VS Code panel reads `notifyOnComplete` the same way next to its own `oxide.notifyOnFinish`, so turning notifications off in the terminal silences it too (a VS Code notification carries no sound of its own, so `notifySound` is the CLI's and the desktop's). The TUI `/notify [on|off]`, `/notify sound [on|off]`, and `/notify test` commands mutate the running config and persist the flags to the global `settings.json` through `save` (`OXIDE_SETTINGS_FILE` overrides the path). The TUI only toasts for real agent runs (internal work like `/compact` and branch summaries sets no `App.notify_on_finish`), using a short title pulled from the newest assistant reply (its first non-empty line, with Markdown markers stripped) as the body instead of the whole summary.
- `crates/core/src/session.rs` — Pi-compatible session storage under `sessions/<project>/` in the Oxide config dir. Each file is a JSONL tree: a `session` header followed by `message`, `compaction`, `branch_summary`, `session_info`, `model_change`, and `thinking_level_change` entries carrying `id`/`parentId`/`timestamp`. The last entry is the active leaf; appending adds a child of the leaf, `branch_with_summary` moves the leaf and appends a branch summary, and `context`/`messages` walk the leaf path with the latest compaction applied. A session's `preview` is its first user message summarized by the shared title rules (`crate::title`), so a picker row, the desktop's sidebar and the panel's header agree. Sessions are resumed via `-c/--continue`, `-r/--resume` (session picker), `--session <path|id>`, or `/resume`; `list` returns picker summaries (id, name, preview, message count), `delete`/`rename` manage sessions, `rewrite` rewrites a session as a linear chain, and `fork` seeds a new session from a message slice (used by `--fork`, `/fork` and `/clone`). Appends are fsynced and recover from a partial trailing line; an append to a file that was removed underneath a running session — a delete from another front-end — rewrites the header and every in-memory entry first, so the live conversation continues instead of failing with `No such file or directory`. Reading is cycle-safe: a corrupt file whose entries form a parent/child loop (or whose newest entry points at itself) is walked with a visited set, so `list`, `summary` and `context` terminate instead of spinning — a hang there used to look like a frozen app, since the desktop's sidebar and the CLI's session picker both walk every file. `new_id` mixes the full nanosecond clock into a 64-bit value, so two sessions created in the same millisecond do not collide. Resolving an id to its file is done by name (`<millis>_<id>.jsonl`, with a stem suffix accepted), so resuming a thread in a project whose store holds many sessions — or one 37 MB thread — reads that file instead of parsing every other session to find it, while a file that was renamed still resolves through the header of its first line.
- `crates/core/src/sessions.rs` — non-interactive session management (`oxide sessions list/show/delete/compact/merge`) for stale-session cleanup; `show` prints one session's conversation (the leaf path with the latest compaction applied) as text or as the JSON a front-end draws — id, name, cwd, path, the number of messages in context, how many of them were returned, the messages with their tool calls, and the thread's usage totals — which is what the VS Code panel replays when it resumes a thread; `delete` filters by id/`--all`/`--older-than`, `compact` summarizes older history into a summary plus recent tail (one LLM pass per session), and `merge` concatenates two sessions or summarizes the second one first.
- `crates/core/src/title.rs` — the one-line title rules every front-end names a thread, a session and a finished turn by: the first line that reads as prose (skipping blank lines, a fenced block's contents, a table row and a line that is only punctuation), with its Markdown taken off (`#`/`>`/`-`/`1.` markers, emphasis, code, and a link or image reduced to its text) and collapsed, then cut to `TITLE_LIMIT` (64) at a word boundary with an ellipsis. `session::preview_text` (what a session is listed under when it was never named) and the TUI's completion toast use it, so the desktop's sidebar and toast, the terminal's picker and toast, and the VS Code panel's header all say the same thing about the same conversation; the panel is TypeScript and cannot link the crate, so `summarizeTitle` in `editors/vscode/src/core/protocol.ts` mirrors the rules and `test/protocol.test.ts` holds the same cases as this module's tests.
- `crates/core/src/snapshots.rs` — shadow-git snapshots (bare repo under `snapshots/<project>/` in the Oxide config dir) committed after each agent step; `/undo` and `/redo` in the TUI restore file changes. `baseline(&cwd)` records the state a run starts from and returns the revision to compare against, `changes_since(base)` lists the files that changed since it (what the desktop's change card, the VS Code panel's card and `oxide changes show` all read), `content_at(revision, path)` reads a file as that revision recorded it — the left side of a diff, which is nowhere on disk — and `restore_turn(base, after)` puts the work tree back to it, refusing (with the reason) when `after` names a state the tree has moved past, so an older run's restore cannot take a newer one's work with it — the one path behind the desktop's `undo_turn`, the terminal's `/undo` and the extension's `oxide changes undo` (`restore(base)` is the same reset without the guard). A project does not have to be a git clone: the shadow repo is oxide's own, so a plain folder is recorded too, and what `snapshot_scope_is_safe` refuses is only what must not be walked — the volume root, the home directory or an ancestor of it, a directory holding the config directory (which holds the shadow repos themselves), and a directory that is neither inside a git work tree nor project-sized (`EXCLUDED_DIRS`' build output and dependency trees left out of the count), so a turn in a folder that is not a project leaves no listing rather than indexing a whole disk. Everywhere else a git work tree is trusted as it stands, since its own `.gitignore` is what bounds `git add -A`.
- `crates/core/src/changes.rs` — the files a run changed, as a front-end lists them: `ChangeStatus` (`Added`/`Modified`/`Deleted`, with the `A`/`M`/`D` `letter()`), `FileChange` (path, status, the added/removed line counts, `binary`, and the same compact line-numbered preview `crate::diff` renders for a single edit), `TurnChanges` with the totals a card's header shows, and `empty()`. Everything is pure — `parse_name_status` reads `git diff --name-status -z` (a rename's new name is the file to show, since git reports both), `count` reads the `+`/`-` a preview line starts with, and `summarize` adds the entries up — while the git-facing half is `Snapshots::changes_since`, so a file no tool call named is listed the same as an edited one and a file a run deleted reads as deleted rather than as an unstaged removal.
- `crates/core/src/permission.rs` — parses per-agent `permission` rules into allow/ask/deny and decides per tool + subject; `ask` prompts in the TUI unless `auto_approve` is set (the `config.json` key `/approvals on|off` flips), and a `deny` rule reaches an interactive approver instead of denying outright.
- `crates/core/src/approval.rs` — the interactive tool-approval broker shared by the CLI's rpc mode, the TUI and the desktop app: an `Approver` callback that emits `AgentEvent::ApprovalRequest { id, tool, detail }` and awaits the answer for that id — `ApprovalBroker::resolve` for a front-end that has a wire word (`deny`/`once`/`always`, parsed by `Decision::parse`) and `ApprovalBroker::answer` for an in-process one that already has the `Decision` (`Once`, `Always`, or `Deny { message }`, whose message is pushed to the run's `Steering` queue so the agent reads it as guidance). An unknown id means the request already timed out, and an unanswered request denies after `APPROVAL_TIMEOUT` (5 minutes) so a turn cannot hang. `list`/`clear` read and edit the project's saved rules.
- `crates/core/src/approvals.rs` — the persisted side of it: per-project `allow` sets in `<config>/Oxide/approvals.json` (`load`/`is_allowed`/`allow`/`list`/`clear`), migrated once from the desktop's legacy `<config>/Oxide/desktop/approvals.json`, so an `Always allow` answer holds across the terminal, the desktop app and the VS Code extension.
- `crates/core/src/ask.rs` — the interactive question side of an agent run, which is what a skill that needs a decision asks through: the agent-level `ask` tool takes 1–4 questions (`question`, an optional `header` used as the dialog's heading, up to 8 `options` of `label`/`description`, and `multiSelect` for a list more than one label may be picked from; a question with no options is answered in the user's own words), `parse_questions` trims, de-dupes and caps them while accepting a single question object, an option written as a plain string, or a `multiSelect` spelled out as `"true"`, and `format_reply` hands the answer back to the model as the tool's result. `AskBroker` mirrors the approval broker — an `Asker` callback that emits `AgentEvent::QuestionRequest { id, questions }` on the run's own stream and awaits the answer for that id — with `AskBroker::resolve` for a front-end that has wire values (an empty answer list is `Reply::Dismissed`) and `AskBroker::answer` for an in-process one. An unanswered request returns `None` after `ASK_TIMEOUT` (5 minutes), which the tool reports as nobody having answered, so a turn cannot hang, and it emits `AgentEvent::QuestionClosed { id }` as it gives up (framed as `question_closed`, `crates/core/src/cli.rs`) so a front-end that painted the questions stops taking an answer nobody will read; a front-end that answered, or a run that ends with a request still open, already knows and is told nothing. The asker is optional on every run (`Runtime.ask` / `AgentRun.ask` are `Option<Asker>`), so `ask` is only offered where a front-end can answer it — the desktop app and an `--mode rpc` client that passed `--ask-questions` — and a TUI or print run never has the model ask a question nobody can see.
- `crates/core/src/compact.rs` — Pi-style context compaction. Walks back from the newest message until `keepRecentTokens` is reached, summarizes the older span with a structured handoff format (including cumulative read/modified file lists; the format request is sent after the wrapped transcript, matching Pi, so the summarizer does not continue the conversation), and never cuts between a tool call and its result. When the cut lands inside a user turn — the kept tail begins with an assistant message or tool result — the request that opened that turn and the progress before the cut are summarized on their own as a split-turn prefix and merged into the checkpoint (`**Turn Context (split turn):**`), the way Pi handles a split user-message span; a later compaction updates the previous checkpoint through Pi's update prompt instead of writing a fresh one, and each summarization call is capped at a fraction of `reserveTokens` (0.8 of it for history, 0.5 for the turn prefix) so a one-off summary cannot spend the whole response budget. Settings live under `compaction` in `settings.json`/`.oxide/settings.json` (`enabled`, `reserveTokens`, `keepRecentTokens`, per-model `modelOverrides`), with `OXIDE_COMPACTION_*` env overrides. Auto-compaction runs in the agent loop once provider-reported usage crosses `contextWindow - reserveTokens`; it appends a `compaction` entry to the session branch anchored at `firstKeptEntryId`, and the session rebuilds the outgoing view from the leaf path — the anchor is resolved through `context_ids`, which lists only entries that carry a message (a name, model or thinking-level change contributes no message and would otherwise shift the boundary onto a neighboring entry), so a call and its results are never split by a bookkeeping entry. Branch summarization reuses the same structured format: `/tree <n>` branches the current session in place (appending a `branch_summary` entry) and `/fork <n>` creates a new session seeded with the summarized abandoned path. Manual compaction is `/compact [focus]` (TUI) and `oxide sessions compact`.
- `crates/cli/src/tui/markdown.rs` — dependency-free Markdown renderer for assistant messages: parses headings, paragraphs, fenced code, ordered/unordered/nested lists (with `☐`/`☑` task markers), blockquotes, rules, pipe tables, and inline bold/italic/strike/code/links/autolinks (a bare `http(s)://…` written without brackets is one too, and `take_bare_url` is the one rule the renderer and the transcript's click handling share) into styled `ratatui` lines wrapped to the pane width — a labelled link drawing its label alone, with the URL it names riding on the label's own characters (`Inline`) and the range they end up covering recorded on the row they land on (`Rows::links`), so the transcript's click handling still finds it and two labels that read the same keep their own targets. `render_with_prefix` merges the `◆ oxide` speaker label onto the first line by wrapping the body with that line's width reserved (`Renderer::first_width`, which every block honours, taking off the indent a list marker, quote bar or ambient already carries), because wrapping the body first and re-wrapping only its first line breaks the paragraph twice and orphans its tail; unclosed delimiters stay literal so a reply renders cleanly while it streams.
- `crates/core/src/diff.rs` — dependency-free line diff for the TUI: `preview(old, new)` returns `None` when unchanged, a one-line summary when either side exceeds `MAX_DIFF_LINES`, otherwise an LCS-based unified-style preview that keeps `CONTEXT` lines around each change and inserts `⋯` gap markers between disjoint hunks. `lines(old, new)` is the same alignment as the lines themselves — each carrying its `LineKind` and the number it holds on each side, and none on the side it is missing from, with `Diff::Same`/`Diff::Omitted` for the two cases a preview renders as a summary — which is what a front-end painting both sides of a change reads.
- `crates/core/src/html.rs` — dependency-free HTML to Markdown/plain-text conversion for `webfetch`: a small tag parser, entity decoding, and a renderer for headings, paragraphs, lists, tables, links, images, code, and blockquotes.
- `crates/core/src/child.rs` — the one rule for a child oxide starts over pipes (`tools::bash`, an LSP server, an MCP server, the plugin host): `detach_terminal` gives it a session of its own, and with the session no controlling terminal. A child otherwise inherits oxide's session and the terminal the front-end is drawing on, so a program that opens `/dev/tty` for an answer of its own — zsh's `compinit` asking whether to keep an insecure directory, a credential or passphrase prompt, a pager — writes into cells no frame of the TUI's buffer holds: ratatui only repaints cells whose style changed, so the prompt stayed over the conversation, the composer and the message being typed in it, while the keys typed there answered the child instead. Detached it fails with the reason in its own captured output instead (a `compinit` behind it says `not interactive and can't open terminal` and aborts, so the turn reports why it could not initialize rather than hanging on a question nobody saw), the detach is a `pre_exec` `setsid` whose failure is reported rather than swallowed, and on Windows the same rule is `CREATE_NO_WINDOW` — redirecting a child's standard handles leaves it attached to the console the front-end draws on, where `CONOUT$` paints over the interface and `CONIN$` reads the keys typed into it — the flag the image helpers in `media.rs` already use, while a target that is neither Unix nor Windows has nothing to do.
- `crates/core/src/lsp.rs` — minimal LSP client (rust-analyzer, typescript-language-server, pyright, gopls) that reports diagnostics; a `diagnostics` tool is exposed and `write`/`edit` append diagnostics for the edited file. A cached server that exits or whose pipe breaks is evicted from the manager (killing the child) and a fresh one is connected before the call is retried, so a one-off crash does not turn every later edit into `Broken pipe`; EOF while awaiting diagnostics is treated as a disconnect rather than a clean result. A server that still cannot be talked to after the fresh attempt is treated as absent — remembered so it is not respawned, and reported as no diagnostics — so a broken toolchain (a `rust-analyzer` shim missing from the active toolchain, say) does not append `lsp server closed the connection` to every edit.
- `crates/core/src/plugin.rs` — plugin runtime: loads discovered JS/TS plugins under bun/node with an embedded harness and dispatches `tool.execute.before` / `tool.execute.after` hooks. An `after` hook can rewrite the output and set `output.terminate` to end the turn; a `status` hook returns keyed strings for the footer's third row.
- `crates/core/src/pricing.rs` — model prices for the footer's `$cost` segment. Ships a small default table (USD per million tokens, including the GLM models) overlaid by a `modelPrices` map in `settings.json`/`.oxide/settings.json`; unknown models cost 0 and the segment is omitted.
- `crates/core/src/portkey_usage.rs` — the Portkey spend status bar, behind `/spend` in the TUI, which opens a settings dialog (`Enabled`, `User`, `Metadata`, `Budget`, `Currency`, `API key`, `Endpoint`; the typed `/spend on|off|user|budget|currency|key|metadata|status` forms still work) — the shared `/usage` is a different command, this chat's own tokens, cost and context window, and takes no arguments (it only runs while a Portkey provider is logged in, since it reads that account's spend); settings and the API key live in `portkey-usage.json` in the Oxide config dir (mode 0600, `OXIDE_USAGE_FILE` override). `spend` queries `GET <base_url>/analytics/graphs/cost` with `x-portkey-api-key` filtered by the configured user metadata (`_user` by default) for the local day and month, and the bar adds the session's own `$cost`; the key falls back to the active Portkey credential, the budget is formatted in the configured currency (`usd`/`cny`), and the bar refetches every 60s and after each turn.
- `crates/core/src/plugin_registry.rs` — Claude Code-style plugin packages and marketplaces: `oxide plugin` subcommand plus the TUI `/plugins` and `/marketplaces` surfaces manage marketplaces (`.oxide/marketplace.json` preferred, `.claude-plugin/marketplace.json` compatible) and installed plugins (`.oxide/plugin.json` preferred, `.claude-plugin/plugin.json` compatible, bundling commands, agents, skills, MCP servers, and command hooks) under `<config>/Oxide/plugins/`. `marketplace_overview()` shapes each marketplace and its plugins (with local install/enable state) for the `/marketplaces` browser, whose two-pane overlay lists marketplaces on the left and the selected marketplace's plugins on the right (Tab switches pane, Enter installs/removes/toggles, Ctrl+U fetches a git marketplace's latest manifest via `update_marketplace`, Ctrl+A adds, Ctrl+X removes, Ctrl+R reloads the local view). Typing filters the focused pane, with plugin names matched before descriptions. Installed plugins load into the ecosystem before project resources; manifest hooks are translated into a generated JS shim run by the hook host. `enabled_plugins()` returns the enabled packages that still have a directory and a manifest (what `load_enabled_plugins` loads), and `installed_plugins()` every installed one with its `enabled` flag, enabled first and then by name, so a front-end can name a plugin the user has already installed instead of offering it as something to install again.
- `crates/core/src/tools.rs` — tool specs and execution under Pi-style names (`read`, `write`, `edit`, `bash`, `grep`, `find`, `ls`, `webfetch`) plus connected MCP tools; legacy aliases (`read_file`, `write_file`, `patch`, `list_dir`, `glob`) are accepted via `canonical_tool_name`, which every name comparison routes through. `execute(call, cwd, &McpRegistry, &Progress)` returns a `ToolOutput` (text plus optional content parts the bytes decide — an image, a PDF or the file's own text, named in the result by `media::part_kind` — an optional `DiffPreview` for `write`/`edit`, and a `terminate` flag; `read` attaches whatever `media::is_attachment_path` accepts as media, which now includes an image format `oxide_core::media` converts); `bash` streams stdout/stderr through `Progress`. Output is capped centrally in `execute` by lines (`MAX_OUTPUT_LINES`) and bytes (`MAX_OUTPUT_BYTES`): `bash` keeps its tail so the exit code survives, other tools keep the head, and dropped content is written under `truncated/` in the Oxide config dir (`OXIDE_TRUNCATION_DIR`, retained 7 days) with a pointer in the result. `read` splits lines longer than `MAX_LINE_LEN` into continuation chunks and pages via `offset`/`limit`, so a minified JSON line can be read through instead of being cut off, and its output budget reserves a line for the `… more lines; use offset=` pointer so the continuation hint is never trimmed. Argument shapes models get wrong are tolerated: `offset`/`limit` accept a numeric string or a range array (`[820, 850]`, which sets the span), and `edit` repairs a stringified `edits` array that was closed with one brace too many (`[{"oldText":…}}]`). A non-exact `oldText` still lands when only trailing whitespace differs or it was copied from `read` without stripping its `N|`/`N+|` numbering; every edit in a call is matched against the original file (so an earlier edit cannot invalidate a later one) and overlapping ranges are rejected instead of guessed, while a genuinely stale one fails with the closest region (its line range and raw text) to copy or, for a block that matches nowhere, a note that each call edits one file. A `bash` command that hits its timeout returns the output it produced before being killed instead of discarding it, plus a hint that steers the retry to a narrower command (a directory scope, a build-output exclusion, or the `grep`/`find` tools) instead of letting the same one time out again. A failed command whose output shows an unresolved relative import (`Cannot find module './...'`) gets a hint: when the Node require stack names a script outside the working directory the hint steers to a script inside the project or an absolute path, and otherwise it steers to checking the specifier, since Node resolves `require('./...')` against the script's own directory, not the working directory. `read`/`ls`/`find`/`grep` accept absolute paths; `ls` renders symlink targets as `name -> target`; `grep` matches a literal substring by default (set `regex: true` for a regular expression) and prefers `ripgrep` when it is on `PATH`, falling back to a parallel built-in walker that sniffs and skips binary files. A search that found nothing answers in Pi's own words rather than with an empty string, which reads as a failure and invites a retry — `NO_MATCHES` (`No matches found`) for `grep`, `NO_FILES_FOUND` (`No files found matching pattern`) for `find` — while an `edit` keeps Pi's `Successfully replaced N block(s) in {path}.`: the redundancy a reader sees is the renderer's to drop, not the result's, which is why Pi's `renderers/edit.ts::formatEditResult` returns nothing on success and the TUI paints `Edited <path>` plus the diff with no restatement line.
- `crates/core/src/cli.rs` — Pi-compatible non-interactive surface: `@file` argument expansion, the `--tools`/`--exclude-tools` `ToolFilter`, Pi-shaped JSON event framing (`--mode json`) with usage events and the `thinking_done` step marker (`ThoughtDone`), and the `--mode rpc` JSONL loop. `event_json` also frames a tool approval as `{"type":"approval_request","id","toolName","detail"}` and a skill's question as `{"type":"question_request","id","questions"}`, plus `{"type":"question_closed","id"}` for the request the broker gave up on when nobody answered in five minutes, so a client hides a dialog it painted instead of offering an answer nothing will read; host messages share stdout with the events — the session header, and a finished run's `turn_changes` frame — and are written ahead of the events behind them (the loop polls the control channel first and drains both before it returns), so a change listing lands where the turn ended rather than after the first tokens of a prompt the client had already queued, and a frame still queued when the last event was written is not lost with the run; `RpcRequest` (`prompt` with its `images`, `approval` with the `deny`/`once`/`always` decision, `question` with the `answers` that settle one — an empty list is a dismissal — and `quit`/`abort`) parses what a client writes back on stdin, which is what lets `run_rpc` answer an approval or a question mid-turn through the shared `ApprovalBroker` and `AskBroker`; only a client that passes `--ask-approvals` is asked (`run_rpc_mode` then clears `auto_approve`), and only one that passes `--ask-questions` is sent a question, so a caller that does not understand either frame never waits on one it cannot see. `-p/--print` buffers a step's text until it commits (a tool call or the turn ending) and clears it on a retry, so a dropped stream never duplicates a partial answer on stdout.
- `crates/core/src/updates.rs` — the release trains, resolved once for every front-end: `Component` (`Cli`/`Desktop`/`Extension`, each with its tag prefix and the label a dialog names it by), the `Release`/`Artifact`/`Check` shapes a front-end reads (a release read from the API carries its own `notes` — the Markdown changelog GitHub holds — and the `released_at` day it went out, which `Check` passes on so a dialog can show what changed instead of sending the reader to the release page for it), and `latest()`/`manifest_release()`/`api_release()` — the newest release of a component, preferring the `Oxide-manifest` the installers read and falling back to the API's release list filtered to that component's tags, so a `desktop-v*` or `extension-v*` release is never mistaken for a CLI one; `platform()` picks the artifact this machine installs out of a release, with the digest GitHub reports beside it: the desktop app's are its installer's own names, which drop the version — `macos-arm64-Oxide.dmg`, `linux-<arch>-Oxide-Setup.AppImage`, `linux-<arch>-Oxide-Setup.tar.gz`, `win-x64-Oxide-Setup.exe` — and an Intel Mac has none, since the app is built for Apple Silicon alone. `is_newer`/`should_install` are the SemVer comparison (`+…` build metadata carries no precedence, a numeric pre-release identifier comparing as a number, an unparseable version — a source build's `0.0.0` — treated as older so an update is offered), `fetch`/`download` the transfer — `download_reporting` being the same download with a callback per chunk, which is handed the bytes written and the size the response announced and which answers whether to go on, so a front-end that has been asked to stop stops it where it is — `verify_sha256` the checksum, and `WorkDir` the private 0700 scratch a download lands in. `oxide update` (the CLI's own train), `crates/desktop/src/update.rs` (the app's) and the VS Code panel's check all resolve through here, so what a release is and which tag belongs to whom is answered once.
- `crates/core/src/update_notice.rs` — the "update available" notice a launch shows, held once so every front-end reads the same answer: the newest release of a component, remembered in `updates.json` beside `config.json` as a `Notice` (version, tag, the release page, and when it was found) and read back on the next launch whether or not it could be refreshed, because a launch must not wait on the network for it. `refresh` looks the release up through `crate::updates` and remembers it, and an answer older than `REFRESH_AFTER_SECS` (6 hours) is the only one a launch looks up again — long enough that a daily launch costs one request, short enough that a release cut today is offered tomorrow. `Notice::is_update_for` is the shared SemVer comparison (`is_newer`), so a source build's `0.0.0` is offered the release while a newer running version is not. `checkForUpdates` in `settings.json` — the project's `.oxide/settings.json` winning over the global one, `OXIDE_CHECK_FOR_UPDATES` overriding both — decides whether a launch looks at all, on by default, and `enabled`/`save` are that flag read and written (`OXIDE_UPDATES_FILE` redirects the file, which is how a test or a caller with its own config directory points it elsewhere). The terminal is the front-end that shows it (`ChatItem::Update`); the file is per component, so a front-end that offers another train's notice neither waits for nor overwrites this one's answer.
- `crates/cli/src/install.rs` — how the running binary was installed, held once for `oxide update` and `oxide uninstall`: `detect_install_method` recognizes a Homebrew Cellar, Cargo's `~/.cargo/bin`, and the `~/.local/bin` or `%LOCALAPPDATA%\Programs\Oxide` a prebuilt archive is unpacked into — and any other directory marked by the `.oxide-install` file `record` writes beside the binary, which both installers leave and `oxide update` rewrites when it replaces one, so a custom `OXIDE_INSTALL_DIR` is still a released install — and reports `Unknown` for anything else — a `target/debug` build, a distribution package, a binary someone moved — so a command that is about to replace or remove it checks before it does.
- `crates/cli/src/update.rs` — `oxide update`: resolves the newest CLI release from the shared `oxide_core::updates` (`--component cli`, its default) and installs it the way the installers do — verifying the archive against the checksum, unpacking into a private temp directory, running the unpacked binary's `--version` before it replaces a working one, then renaming a copy beside its destination — while the resolution itself (which tag belongs to which component, the platform artifact, SemVer, checksums) lives in `crates/core/src/updates.rs`, so `oxide update --check --json --component desktop|extension --current <v>` answers the same question for a front-end that installs that release itself: the desktop app's **Check for Updates…** (`crates/desktop/src/update.rs`) reads it for a `desktop-v*` bundle and the VS Code panel (`editors/vscode/src/core/updates.ts`) for an `extension-v*` `.vsix`. `--version` takes a tag or a bare version, `--check` reports and stops, and `-f/--force` reinstalls — see the module docs for the details of each.
- `crates/desktop/electron/` and `crates/desktop/src/` — the app in two halves, joined by one JSON packet per line on a pipe. `electron/main.ts` is the window: it starts the harness beside it, creates the one window over `ui/index.html` with `contextIsolation` off and `nodeIntegration` off, so the page keeps the world its own script was written for while Node stays out of it and `electron/preload.ts` is the only thing in that world that touches `ipcRenderer` — it installs exactly the three globals the page has always read (`__electrobunHostBridge`, `__electrobun.receiveMessageFromHost` and the queue between them, the names kept because renaming one would mean editing the page it exists for); it lets the window show its own page and nothing else of the config directory the CLI reads (`app.setPath("userData", <appData>/Oxide/desktop/electron)`), builds the menu bar itself (`Menu.buildFromTemplate`: the platform's roles, plus the one **Check for Updates…** click, which is announced to the page as the `check-updates` event the sidebar's own button raises), forwards the page's packets to the harness's stdin and every line back to the page - `electron-builder.yml` — the packaging the app updates itself through: Electron's files are the app, `electron/dist` the compiled window and `ui/` the page, with the harness carried beside them as a resource (`extraResources`, `target/release/oxide-desktop` into `Resources/harness/`) and started as a child process; it is signed as part of the bundle (`binaries`, the macOS entitlements) rather than being code the app loads. - `crates/desktop/src/update.rs` — the desktop app's own release train: `installation()`/`installation_of()` read what this copy is — a macOS `Oxide.app` bundle, an AppImage (found through the `APPIMAGE` its runtime sets, since the executable inside a mounted one is an unpacked copy), the copy a Windows setup made (found by its executable under `%LOCALAPPDATA%\Programs\<app>`, told apart from a folder that merely holds the program by the uninstaller the setup writes beside it), or a checkout's build the app does not replace — and whether it may be written over from inside the app, probed by writing a file beside it rather than read off a mode bit, since a mode bit says nothing about who is running; `cancel()` is the flag the download checks between its chunks, which stops the install before anything is put in place and is reported as `CANCELLED` rather than as a failure (`was_cancelled`). ## Conventions

- Rust 2021 edition, 4-space indent, default rustfmt style.
- Errors use `anyhow::Result` with `.context(...)` / `.with_context(...)` for human-readable messages.
- Do not add comments unless they explain non-obvious intent.
- Keep changes small and focused; verify with `cargo test` and `cargo clippy`.
- Built-in file/shell tools and connected MCP tools are registered in `tools::specs(&McpRegistry)` and dispatched in `tools::execute(call, cwd, &McpRegistry, &Progress)`. Tool names are canonicalized with `tools::canonical_tool_name`, which accepts Pi names (`read`, `write`, `edit`, `ls`, `find`) and legacy names (`read_file`, `write_file`, `patch`, `list_dir`, `glob`); permission rules, concurrency checks, and TUI rendering must go through it. `edit` is targeted text replacement (`edits[].oldText` must match uniquely against the original file) and stays separate from the unified-diff `patch` tool. Matching is byte-exact first, then a line-wise pass that ignores trailing whitespace, and a block copied from a numbered `read` listing has its `N|`/`N+|` prefixes stripped (from the replacement text too); leading indentation is never ignored, so a replacement cannot silently lose its indentation. A non-unique match is still rejected, naming the occurrence line numbers, an absent one names the closest region (its line range and raw text, so copying it back applies exactly), and every failing edit in a batch is reported together while nothing is written. `find`/`grep` honor `.gitignore`; `grep` prefers `ripgrep` when available and otherwise uses a parallel built-in walker. The agent-level `task`, `skill`, `command`, `memory`, `diagnostics`, and `ask` tools are defined and dispatched in `crates/core/src/agent.rs`.
